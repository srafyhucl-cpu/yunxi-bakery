# Project Boundaries

本文件把 `YunxiBakeMiniApp` 明确为 `Bakery Commerce Platform` 的 `Storefront MiniApp` 渠道仓。

## 项目定位

`Bakery Commerce Platform` 是总体产品逻辑名。`YunxiBakeBot` 是当前 `Platform` 主仓，承载业务真相、后台能力和第三方集成。`YunxiBakeMiniApp` 是面向消费者的微信小程序前台渠道仓。

`Yunxi` 只是首个落地实例 / 租户名，不是产品总名。当前阶段不改仓库 slug、不改部署路径、不改线上 API 契约，也不改页面业务行为。

## 本仓负责

- 小程序页面、组件、交互和视觉呈现。
- 微信小程序能力接入，包括登录、授权、支付唤起、路由、分享、本地缓存和本地会话状态。
- API client，包括请求封装、参数组织、响应适配、错误信息传递和前台兜底展示。
- 前台本地状态，例如购物车、地址选择、页面临时状态、轻量缓存和离线/开发兜底数据。
- 面向小程序体验的格式化、展示映射和 UI 状态组织。
- 客户群触达的前台承接页，例如根据 Platform 生成的 `campaignId` 打开登记表、校验并提交用户填写的信息。

## 本仓不负责

- 客户主档和会员主数据。
- 商品规则真相，包括分类、价格、库存、上下架、规格、同步状态和第三方商品映射。
- 订单规则真相，包括价格计算、库存预占/释放、支付状态、履约状态流转和订单归属校验。
- CRM 逻辑、营销规则、客户运营策略和后台经营看板。
- AI 会话主逻辑、知识库、客服编排、转人工队列和人工客服后台。
- 店铺配置真相、后台配置系统、装修发布系统和配置审核流程。
- 有赞、微信支付、企业微信或其他第三方集成的同步真相。
- 后端持久化、数据迁移、支付回调、定时任务和对账任务。
- 企业微信客户群内实时机器人回复、群身份映射真相、活动链接生成、登记记录后台汇总和客服跟进工作台。

## 依赖关系

本仓通过 `miniprogram/services/` 调用 `YunxiBakeBot` 暴露的 `Platform` API。接口契约记录在 `docs/api-contract.md`，服务代码只负责把小程序页面需要的请求组织好，并把响应适配成页面可消费的形状。

如果页面需要新的客户、商品、订单、AI、配置或第三方集成能力，应先回到 `Platform` 主仓定义业务真相和 API 契约。本仓只能补充契约文档、API client 和页面调用，不应在前台复制一套规则中心。

客户群运营也遵循同一边界：`YunxiBakeMiniApp` 可以承接从群内打开的小程序登记链接，但 `campaignId` 生成、群归因、登记汇总、状态变更和客服分配都属于 `Platform`。在 `opengid_to_chatid` 或企业微信群身份能力未接入前，前台不得自行推断群身份。

## 过渡态说明

当前后台配置仍嵌在 `YunxiBakeBot` 管理页中，这是过渡态，不是长期架构。它说明当前 `Platform` 主仓临时承载后台配置能力，不说明 `YunxiBakeMiniApp` 应该实现后台配置系统。

长期方向应保持：

- `Platform` 主仓负责配置编辑、保存、发布、审计和第三方同步。
- `Storefront MiniApp` 只读取已发布给小程序的公开配置。
- 小程序可保留开发兜底和展示兜底，但不得把兜底逻辑升级为业务真相。

## 禁区规则

后续不得在本仓新增以下能力作为业务真相：

- 客户主档逻辑。
- 商品规则真相。
- 订单规则真相。
- CRM 逻辑。
- 第三方同步真相。
- 后台配置系统。

如因联调或临时演示需要保留 mock、兜底或展示映射，必须在代码或文档中明确它是前台体验兜底，并在最终真相来自 `Platform` API 时优先使用后端结果。
