# Bakery Commerce Platform 历史 Harness Engineering 成熟度评估报告

> 说明：这是 2026-06-04 时点的历史评估报告，保留当时的项目口径和判断，用于回溯，不代表当前设计现状。

> 评估时间：2026-06-04 | 版本：v0.8.0 | 评估框架：Harness Engineering 六层模型 + 五级成熟度

---

## 零、什么是 Harness Engineering

> Agent = Model + Harness。模型提供推理能力，**Harness 是模型之外的整套约束、验证、反馈与控制系统**。

本报告从两个维度评估项目的 Harness 体系：

| 维度 | 参考框架 |
|------|---------|
| **六层覆盖度** | L1 环境门禁 → L6 运行时健康，逐层评估 |
| **五级成熟度** | Level 0（无 Harness）→ Level 4（自治循环），定位当前阶段 |

## 一、六层 Harness 覆盖度评估

### 总览矩阵

| 层 | 名称 | 覆盖度 | 核心制品 |
|---|------|--------|---------|
| L1 | 环境与配置门禁 | **强** | config.py、.secrets.baseline、VERSION、pip-compile 锁文件、Dockerfile |

### L1：环境与配置门禁

> 解决什么问题：Agent 该知道什么、不该知道什么

| 制品 | 约束机制 | 评分 |
|------|---------|------|
| `app/config.py` | pydantic-settings 集中管理所有配置，密钥不进仓库 | ★★★★☆ |
| `.secrets.baseline` | detect-secrets（18 种检测器 + 11 个过滤器），阻断密钥泄露 | ★★★★★ |
| `VERSION` + `sync_version.py` | 版本号单一来源，自动 semver 递增 | ★★★★★ |
| `requirements.in` + `requirements.txt` | pip-compile 锁文件，可复现构建 | ★★★★☆ |
| `Dockerfile` + `docker-compose.yml` | 容器化部署，资源限制 4G/2CPU | ★★★★☆ |
| `AGENTS.md` | AI coding agent 入口约束文档，含 6 大类规范 | ★★★★★ |

**层评分：A（优秀）**

亮点：双重密钥防护（正则红线 + detect-secrets）+ 版本号单一来源 + AGENTS.md 作为 Agent 的"岗位说明书"

---

### L2：静态分析红线

> 解决什么问题：Agent 怎么不跑偏

**本项目是整个 Harness 体系中最强的层**，通过 `check_project.py` 实现了 10 条阻断级红线规则：

| # | 规则 | 类型 |
|---|------|------|
| 1 | 禁止 `Optional[X]` / `Union[X,Y]` | 代码风格 |
| 2 | 禁止 `# TODO` 占位符 | 质量控制 |
| 3 | 禁止 `SELECT *` | 数据库规范 |
| 4 | **api 层禁止直接导入 repository** | **架构分层约束** |
| 5 | **service 层禁止直连 aiosqlite** | **架构分层约束** |
| 6 | **models 层禁止引用上层模块** | **架构分层约束** |
| 7 | 禁止 SQL f-string 拼接 | 安全 |
| 8 | 禁止静默吞异常 | 质量控制 |
| 9 | 禁止硬编码密钥 | 安全 |
| 10 | 禁止裸 `print()` | 代码风格 |

**额外的洁净代码检查**：

| 检查项 | 约束 |
|--------|------|
| 函数体内禁止硬编码平台 URL | 必须通过模块级常量引用 |
| 函数体内禁止已知魔法整数 | 172800/86400/43200/604800 等秒级常量 |
| 函数体行数 > 50 | 警告（不阻断，渐进式收紧） |

**文件体量门禁（`check_file_sizes.py`）**：

| 层级 | 上限 | 存量豁免 |
|------|------|---------|
| `app/repository/` | 250 行 | 1 个文件（knowledge_repo.py） |
| `app/service/llm/` | 180 行 | 2 个文件 |
| `app/service/youzan/` | 250 行 | 1 个文件（event_item.py） |
| `app/service/` | 320 行 | 2 个文件（chat.py, observability.py） |
| `app/api/` | 350 行 | 无 |
| `app/`（兜底） | 400 行 | 1 个文件（database.py） |

**层评分：A+（卓越）**

亮点：
- 10 条红线全覆盖代码质量、架构、安全三大维度
- 分层差异化文件阈值（底层限制更严），精细化治理
- 渐进式策略：存量豁免 + 增量阻断，务实可落地
- 引用 OpenAI 的理念："If it cannot be enforced mechanically, agents will deviate"（不能机械化执行的约束，Agent 迟早偏离）

### L3：文档与流程门禁

> 解决什么问题：Agent 做的事有记录、可追溯

| 制品 | 约束机制 | 评分 |
|------|---------|------|
| `check_logbook.py` | 代码变更必须同步 LOGBOOK + 项目进度清单，否则阻断提交 | ★★★★★ |
| `sync_version.py` | 基于 Conventional Commits 自动 semver 递增 + 文档注入 | ★★★★★ |
| `LOGBOOK.md` | 项目演进编年史，每次变更必须记录 | ★★★★☆ |
| `项目进度与配置清单.md` | 进度跟踪 + 已知问题清单 + 版本号自动同步 | ★★★★☆ |
| Conventional Commits | 标准化提交信息格式 | ★★★★☆ |

**层评分：A（优秀）**

亮点：
- `sync_version.py` 与 `check_logbook.py` 分工明确：版本自动化 + 文档阻断
- 版本号自动注入到进度清单，消除手动同步的人为错误
- LOGBOOK.md 声明为"项目演进的唯一真实编年史"

### L4：测试覆盖率门禁

> 解决什么问题：Agent 怎么知道自己做对了

| 制品 | 约束机制 | 评分 |
|------|---------|------|
| `pytest.ini` | `--cov-fail-under=70` 覆盖率门禁 | ★★★★☆ |
| 测试套件 | 118 个测试用例 | ★★★☆☆ |
| 覆盖率报告 | html + xml 双格式输出 | ★★★★☆ |
| CI 归档 | 覆盖率报告保留 7 天 | ★★★☆☆ |

**层评分：B+（良好）**

亮点：覆盖率阈值 70% 是合理的起点
缺口：
- 118 个测试用例对应 82 个 .py 文件，覆盖密度分布不均匀
- L2 的红线规则本身没有自测（如果规则正则写错了，没有测试能发现）
- 关键路径（webhook 处理、支付回调）缺少针对性测试

### L5：CI/CD 自动化门禁

> 解决什么问题：Agent 的产物能否通过完整流水线

| 步骤 | 机制 | 评分 |
|------|------|------|
| 红线扫描 | `check_project.py` 阻断级 | ★★★★★ |
| 单元测试 | `pytest --cov-fail-under=70` | ★★★★☆ |

### L6：运行时健康门禁

> 解决什么问题：Agent 上线后怎么监控和恢复

| 制品 | 约束机制 | 评分 |
|------|---------|------|
| `/health` 端点 | CI 轮询 + Docker HEALTHCHECK | ★★★★☆ |
| `app/logger.py` | 结构化日志 | ★★★★☆ |
| `app/service/observability.py` | 数据观察台（353 行） | ★★★★☆ |
| `docker-compose.yml` | 容器资源限制 + 健康检查 | ★★★★☆ |
| 生产告警 | 无自动告警机制 | ★☆☆☆☆ |
| 自动恢复 | 无自动重启/回滚机制 | ★☆☆☆☆ |

**层评分：C+（需要加强）**

亮点：结构化日志 + 可观测性基础已搭建

- 缺少自动恢复机制（systemd 的 `Restart=always` 仅覆盖进程崩溃，不覆盖逻辑故障）
- 可观测性平台（353 行）目前主要是查询面板，缺少自动异常检测

## 二、五级成熟度定位

| 阶段 | 特征 | 工程师角色 | 本项目匹配度 |
|------|------|-----------|------------|
| **Level 0：无 Harness** | 直接给 Agent Prompt，无结构化约束 | 手动写代码 | — |
| **Level 1：基础约束** | AGENTS.md + 基础 Linter + 手动测试 | 主要写代码 | — |
| **Level 2：反馈回路** | CI/CD 集成 + 自动化测试 + 进度追踪 | 规划和审查为主 | **← 当前** |
| **Level 3：专业化 Agent** | 多 Agent 分工 + 分层上下文 + 持久化记忆 | 设计环境 | ☐ |
| **Level 4：自治循环** | 无人值守并行 + 自动清理 + 自修复 | 架构设计 | ☐ |

### 当前定位：Level 2（反馈回路）

**判定依据：**
1. AGENTS.md + 完整 pre-commit 体系（Level 1 特征已完备）
2. CI/CD 集成 + 自动化测试 + 覆盖率门禁（Level 2 标志）
3. 版本号自动递增 + 文档同步门禁（超出 Level 2 常见水平）

**距离 Level 3 的差距：**
- ❌ 无多 Agent 专业化分工（单 Agent 模式）
- ❌ 无持久化记忆系统（跨会话状态管理）
- ❌ 无分层上下文按需加载（AGENTS.md 约 200 行，未做子文档拆分）
- ✅ 分层架构约束已建立（api/service/repository/models）
- ✅ 文件体量差异化阈值已建立

## 六、核心结论

本项目在 **Level 2 中属于高水平**——它的 Harness 体系不是"能用就行"，而是在 L1/L2/L3 三层做了充分且精细的设计（10 条红线、7 层文件阈值、双重密钥防护、自动化 semver）。

**但 Harness 有个隐含的前提：每一个组件都在假设"模型自己做不好这件事"**。随着底层模型能力提升，部分 Harness 规则可能变成冗余的约束。建议每季度重新审视一次红线规则的有效性，该删的删，该加强的加强。
