Harness Engineering · Before / After

不是合并文档，而是给 Harness 一个清楚的家

这一波调整的核心，是把原本散落在多个位置的 Harness 文档，收进同一个父目录。 内容仍然分工明确，但入口统一、命名统一、路径统一，后续 AI 和人都不用在文档树里猜路。

只需要记住这一个入口
docs/harness-engineering/README.md

从这里进入，再按场景跳到 core、adr、specs。脚本仍在 scripts，证据仍在 reports/harness。

前

散点式入口

每份文档都有价值，但路径像散开的面粉袋。

核心规则在 docs/harness/ 追溯、验证、防重犯、交接、证据索引都在这里，但不是唯一父入口。
决策记录在 docs/adr/ ADR 是独立目录，逻辑上属于 Harness，但视觉上像另一个系统。
设计规格在 docs/superpowers/specs/ 生产级设计和其他 superpowers spec 混在一起，查找成本偏高。
根 README 列出很多细链接 入口信息过多，读者会先看到文件清单，而不是文档结构。
后

父目录统一管理

保留分工，但把所有 Harness 文档收进一个清楚的柜子。

统一父入口：docs/harness-engineering/ 从 README 进入，先看目录地图，再按场景选择子文档。
core/ 放日常规则 traceability、verification、mistake ledger、handoff、evidence index 全在 core。
adr/ 放长期决策 为什么采用 Traceable Memory Harness，不再散落在聊天或临时文档里。
specs/ 放大图和路线 生产级设计文档收回 Harness 父目录，不再混在别的 spec 体系里。
New Folder Map

现在的目录心智模型

这不是把所有东西塞进一个大文件，而是像大厂工程文档那样：一个父目录，一个 README 导航，三个稳定分区。

日常操作规则

  • traceability-model.md
  • verification-matrix.md
  • mistake-ledger.md
  • agent-handoff-template.md
  • evidence-index.md

长期决策记录

  • README.md：ADR 模板和触发条件
  • 0001-traceable-memory-harness.md
  • 后续关键架构决策继续编号

设计规格和路线图

  • 生产级 Harness 设计
  • P0 / P1 / P2 / P3 路线
  • 适合回看大图，不做日常入口
1

开始任务

读 docs/harness-engineering/README.md，确认场景入口。

2

留追溯

按 core/traceability-model 分配 trace_id，记录来源、决策、验证。

3

做验证

按 core/verification-matrix 选择最小验证和加强验证。

4

沉淀错误

可复用教训写入 mistake ledger，并由 pre-commit 检查结构。

5

归档证据

报告文件放 reports/harness，索引登记到 core/evidence-index。

这次调整解决的“混乱感”

  • 入口过多 → 根 README 只保留一个 Harness 链接。
  • 目录分散 → 文档统一进入 docs/harness-engineering。
  • 职责不清 → core、adr、specs 三个分区各司其职。
  • 不知道先读谁 → 父 README 按使用场景给入口。

保留但不打扰你的东西

  • 脚本仍在 scripts/：因为它们是可执行工具，不混进文档目录。
  • 证据仍在 reports/harness/：报告可能有敏感信息，默认不入库，只保留 .gitkeep。
  • LOGBOOK 仍是编年史：记录发生过什么，不作为日常阅读入口。
  • 项目 README 只放门牌号：详细地图全部交给 Harness 父目录。
一句话总结： 调整前是“几份文档散在不同抽屉”；调整后是“一个 Harness Engineering 文件柜，里面分 core、adr、specs 三层”。你日常只需要记住 docs/harness-engineering/README.md，剩下都由它导航。
