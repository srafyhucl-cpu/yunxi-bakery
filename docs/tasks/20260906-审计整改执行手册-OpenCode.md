## 3. P0-A：事实一致性整改

### A-01 Webhook 事务属主

目标：Webhook 业务事实、审计记录、inbox 幂等状态在同一个外层 UoW 中提交。

执行要求：

- 定位 `backend/app/service/`、`backend/app/repository/` 中的有赞 Webhook 入口、审计仓储和 inbox 仓储。
- 移除高风险路径中仓储内部 `commit`；仓储只执行 SQL，不拥有业务事务。
- 由 Webhook 命令统一创建和提交 UoW。
- 增加失败注入测试：业务写入失败、审计写入失败、重复 webhook、提交前进程异常，均不能留下半完成事实。
- 验证 savepoint、回滚和重复投递后的最终状态。

完成证据：

- 代码检索证明该路径无内部自提交。
- 定向 pytest 覆盖成功、重复、异常和回滚。
- 数据库最终状态断言业务表、审计表、inbox 状态一致。

### A-02 企微同步游标与入队原子性

目标：持久化消息、消息幂等账本和同步游标推进必须由同一个同步命令事务提交。

执行要求：

- 定位企微同步命令、游标仓储、消息 inbox/outbox 或队列仓储。
- 调整顺序和事务边界，消除“游标先提交、消息后入队”的永久漏消息窗口。
- 对分页、重复游标、空页、部分消息失败和提交失败增加测试。
- 证明重跑同步不会丢消息且不会产生重复业务消息。

完成证据：

- 失败注入后游标不会超过已持久化消息。
- 同一外部消息重复拉取只产生一个内部幂等事实。
- 测试输出和证据登记可回放。

### A-03 企微外发重复发送

目标：外部发送、幂等键、重试和完成状态形成可解释的投递合同。

执行要求：

- 先确认企微接口是否支持幂等键或可查询发送结果；不能假设供应商自动幂等。
- 设计并实现发送状态机，至少区分 `pending`、`sending`、`sent`、`unknown`、`failed`。
- 外部成功但本地超时、进程重启、重复消费时，必须可查询或进入人工可处理状态，不能盲目重复发送。
- 将可用的外部消息标识或业务幂等键持久化。
- 增加网络超时、响应丢失、重复消费和人工重试测试。

完成证据：

- 测试证明重试策略不会无条件重复回复。
- 无法证明外部幂等时，必须采用 `unknown` 加查询/人工确认，不得标为 `sent`。

### A-04 储值与积分账务原子幂等

目标：余额、流水、幂等占位、并发更新和补偿事实由服务级命令原子完成。

执行要求：

- 以账户主键锁定或等价 CAS 保护余额并发更新。
- 在同一事务中完成幂等占位、余额变更、流水写入和必要的补偿/拒绝事实。
- 明确重复请求、不同金额复用同一幂等键、余额不足、并发扣减、事务失败的语义。
- 禁止仅依赖流水唯一约束来声称余额安全。
- 为储值和积分分别补充并发和故障注入测试。

完成证据：

- 每个成功命令都有且只有一条可追溯流水。
- 重复命令不重复扣减。
- 并发测试不出现负余额或余额与流水不一致。
- 异常回滚后不存在孤立余额变更。

### A-05 金额模型统一

目标：订单、支付、退款、优惠、储值和积分相关金额使用统一的精确表示。

执行要求：

- 全仓盘点金额字段、DTO、SQL、序列化和计算路径。
- 选择一种全链路合同：数据库整数分或精确 decimal；不得继续混用 SQLite `REAL`、Python `float` 和整数分。
- 统一舍入、税费、优惠、退款和比较规则，并补充边界值测试。
- 迁移必须可回滚、可重跑，并验证历史数据。
- API 文档同步说明金额单位和类型。

完成证据：

- 静态检索无高风险金额路径的隐式 float 转换。
- 1 分、0.01、重复折扣、部分退款和大金额边界测试通过。
- 迁移前后金额守恒报告可复核。

## 4. P0-B：支付、身份和上线门禁

### S-01 真实支付配置隔离

- 生产配置必须拒绝 `ALLOW_MOCK_PAYMENT=True`。
- 微信支付关闭、凭证缺失、回调地址不完整时，启动/ready 必须失败或明确不可上线。
- mock 只能在显式测试环境启用，不能成为默认值或生产后备路径。
- 增加配置矩阵测试：开发、测试、生产和缺失凭证。

### S-02 支付通知与退款闭环

- 支付通知必须校验签名、时间戳新鲜度、nonce/重放和商户/订单关联。
- 明确通知重复、乱序、超时、查询恢复和部分退款语义。
- 串通“通知入口 → 持久事件 → 订单/账务状态 → 退款补偿 → 对账/人工案件”。
- 只用授权测试账号和模拟/脱敏数据；真实验收需负责人书面批准。
- 为每条链路建立可追溯事件 ID 和可回放测试夹具。

完成条件：不能只证明存在 Normalizer 或签名函数，必须证明端到端消费和最终状态。

### S-03 人工接手与企微员工鉴权

- 生产预检必须要求有效的人工接手 `userid`。
- 企微员工身份必须默认开启校验，关闭只能在明确的本地测试配置中使用。
- 验证员工身份、非员工、过期凭证、缺失配置和转人工失败的行为。
- 不得用静态配置存在代替真实授权验收；真实账号验收需负责人批准。

## 5. P1：生产安全与恢复

### S-04 分布式限流和登录防护

- 将限流、后台登录失败计数和封禁状态迁移至共享且具 TTL/原子操作的存储。
- 明确多 worker、多实例、重启和时钟边界行为。
- 增加并发、过期、恢复和绕过 `X-Forwarded-For` 的测试。

### S-05 有赞凭证不进入 URL

- 改为 Authorization header、请求体或 SDK 支持的安全凭证传递方式。
- 禁止 token 出现在日志、异常、追踪、代理访问日志和重定向 URL。
- 增加静态检索和请求记录测试。
- 如第三方协议强制 query 参数，必须隔离专用客户端、最小化日志并登记风险，不得默认为已整改。

### S-06 上传内容真实校验

- 校验大小、扩展名、声明 MIME、魔数和实际解码内容。
- 使用安全图片/文件解码器，拒绝伪装文件、畸形文件和超大资源。
- 文件名、路径和存储键必须不可控地穿越目录。

- 配置测试必须证明生产 compose 不存在不必要的 `0.0.0.0` 暴露。

### O-02 自动发布回滚

### O-03 配置和凭证卫生

### AI-01 不可信输入隔离
