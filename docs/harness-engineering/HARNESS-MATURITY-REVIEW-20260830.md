# Harness Engineering 全面评审（2026-08-30）

> 优先级最后校准：2026-08-31。中文治理已并入 Harness P0 控制面。

> 本文件是本次 Harness Engineering 评审的唯一正式结论入口。它记录评审范围、外部对标、当前成熟度、落后项和后续优先级；动态任务状态仍以根目录 `PROJECT-STATE.md` 为准，历史证据仍以 `LOGBOOK.md` 为准。

## 一、评审结论

当前 Harness **没有落后到需要推倒重来**。项目已经具备较完整的第一代工程化基础：

- `AGENTS.md`、`PROJECT-STATE.md`、`LOGBOOK.md` 和根目录 `ERRORS.md` 已形成中文优先的权威源层级。
- 任务、分支、版本、提交、证据索引、错误账本和交接快照已有机器检查器与 pre-commit 门禁。
- 客户/员工 Agent 已有 golden case、敏感策略、回复回放、RAG 评估和 LangChain/LangSmith 观测相关脚本。
- 生产预检、备份、隔离整改、容器验证、隐私出站和安全出站已有设计或脚本化资产。

但与 2025-2026 年公开的先进 Agent Harness 实践相比，当前体系仍偏重“文档 + 提交门禁”，以下能力还没有形成可执行闭环：

1. **运行契约不完整**：任务有 `trace_id`，但没有统一的 `run_id`、运行输入/输出摘要、工具策略摘要、模型/依赖版本、成本与延迟字段。
2. **权限策略未完全机器化**：允许路径、禁止路径和生产红线已写入规则，但尚缺一个统一的运行时策略快照与变更前后校验。
3. **Harness 自身缺少回归评测**：已有业务 Agent eval，但没有专门衡量“方向一致性、越权率、交接完整率、证据完整率、重复读取成本”的 Harness eval 基线。
4. **回放粒度不足**：已有 trace 和 replay fixture，但尚未要求每次 Agent 任务都能用固定输入、固定策略和固定依赖摘要重放到同一决策阶段。
5. **自动园艺不足**：当前仍依赖人工发现过期链接、重复入口、失效任务指令和陈旧文档；缺少周期性漂移扫描和待处理报告。
6. **持续质量信号不够统一**：测试数量和结果有记录，但成本、延迟、工具调用次数、人工介入、失败分类和“幸运通过”尚未进入统一收口格式。
7. **CI 级别的跨平台收口不明确**：本地 pre-commit 很强，但仓库中没有一个清晰、可发现、可复用的 Harness CI 入口来保证所有 Agent 使用同一门禁。

## 二、外部对标摘要

评审参考了以下公开项目、论文和官方实践（访问日期：2026-08-30）：

| 对标对象 | 可借鉴做法 | 对本项目的启示 |
|---|---|---|
| OpenAI Harness Engineering | 把仓库知识做成可导航地图；通过结构化检查和周期性清理降低上下文熵；要求计划、实现、验证、回顾形成循环 | `README` 和 `AGENTS` 不能只是一份长说明，必须有机器可检查的索引、漂移报告和阶段性清理任务 |
| SWE-agent | 以配置化 Agent、工具接口和 trajectory 为核心，强调可复现执行和失败回放 | 需要把任务运行元数据与工具调用摘要纳入统一 run manifest，而不是只保留最终结果 |
| OpenHands | 将 Agent 运行时、事件流、沙箱、人工介入和恢复边界分开；支持长任务持续运行 | 需要区分“任务事实”“运行事件”“人工批准”和“最终证据”，并为阻塞任务保留恢复点 |
| LangSmith / LangChain | 数据集、实验、评估器、线上追踪和回归比较是同一条链路 | Agent eval 不能只报 `passed/failed`，还要绑定 dataset/version、评估器版本、阈值和与基线的差异 |
| Agent-SafetyBench 等安全评测 | 不只看最终答案，还看过程风险、越权、工具使用和拒答边界 | 高风险工具必须有策略快照、拒绝原因和人工介入记录，避免“结果看似正确但过程越权” |

## 三、本仓成熟度评分

评分含义：0=没有；1=口头约定；2=文档约束；3=脚本或测试；4=提交/发布门禁；5=持续运行、可回放并有趋势基线。

| 维度 | 当前分数 | 现状判断 | 目标 |
|---|---:|---|---:|
| 权威源与中文管理 | 4 | 单一状态、历史、错误入口已收口 | 4 |
| 任务范围与协作边界 | 3 | 有 `allowed_paths`/`forbidden_paths`，但缺统一运行快照 | 4 |
| 验证与发布门禁 | 4 | pre-commit、定向测试、一次性全量收口已明确 | 4 |
| Agent 业务评测 | 4 | golden/replay/RAG/敏感策略较完整 | 5 |
| 运行可观测性 | 3 | 有 trace 和报告，但字段未统一到一次运行 | 4 |
| 回放与来源证明 | 2 | 有 fixture 和证据索引，缺标准 episode 包 | 4 |
| 工具权限与沙箱 | 2 | 红线和生产边界较全，缺策略即代码 | 4 |
| 人工批准与恢复 | 3 | P2、生产和支付已有人工门槛，缺统一恢复点 | 4 |
| 文档园艺与漂移检测 | 2 | 主要靠人工扫描 | 4 |
| CI/跨环境一致性 | 2 | 本地门禁强，统一 CI 入口不够清晰 | 4 |

**综合判断：3.0/5，属于“可控的工程化 Harness”，尚未达到“持续评测、可回放、策略即代码”的下一阶段。**

## 四、必须保持的现有原则

以下原则已经正确，不应因为追逐外部框架而回退：

- 中文优先的人类可读管理；机器字段保留稳定 ASCII。
- `PROJECT-STATE.md`、`LOGBOOK.md`、`ERRORS.md` 三个职责唯一入口。
- 开发期间定向测试；上线候选时一次全量测试并记录耗时。
- 生产、支付、客户数据、旧仓和小程序正式上线边界继续 fail-closed。
- 业务事实层与 AI 编排层分离，框架优先但不把认证、支付、事务、幂等和恢复塞进 AI 框架。
- 不对未知路径、业务数据、生产目录、有效报告或其他 Agent 的有效工件递归删除；清理脚本白名单内的临时/可重建产物可在预览、路径校验和明确授权后递归批量清理；不覆盖其他 Agent 改动，不把历史快照冒充当前事实。

## 五、按优先级的改进队列

> **优先级口径调整（2026-08-31）**：中文治理并入 Harness 的 P0 控制面，不另设“翻译项目”。P0 只覆盖会影响当前状态、责任、证据、交接、权限和高风险用户可见路径的中文治理；全仓注释翻译、低风险文案优化和历史文档清理仍按 P1/P2 排期。P0 表示必须优先处理，不表示当前已经完成。

### P0：Harness 控制面与发布前置（含中文治理）

#### P0-1：中文治理控制面

- 统一 `PROJECT-STATE.md`、`LOGBOOK.md`、`ERRORS.md` 的中文权威源、状态说明和冲突处理；旧仓镜像只能指向权威入口。
- 强制任务、交接、评审、验收和证据摘要使用中文人类可读内容，并保留 `task_id`、`trace_id`、`status` 等稳定 ASCII 机器字段。
- 对高风险用户可见路径（生产开关、支付/退款、数据处理、阻断/批准、API 错误和 CLI 状态）提供中文状态映射；英文只保留协议字段、命令原文和机器枚举。

#### P0-5：临时与可重建产物受控递归清理

- 允许通过 `scripts/cleanup-local-artifacts.ps1` 预览并递归批量清理白名单内的临时/可重建产物。
- 任意路径递归删除、业务数据、生产目录、有效报告和其他 Agent 有效工件继续保持默认阻断。
- 自定义临时目录仅允许工作区或 `D:\Temp` 下的 `.tmp-`/`pytest-` 前缀路径，并须通过 `rebuildable_cleanup` 策略记录明确授权。
- 建立中文治理检查器和覆盖率基线，至少检查权威源漂移、裸机器状态码、关键模板缺字段和高风险路径中文缺失。

完成标准：中文治理成为 Harness 收口条件之一；任何“完成/通过/已上线”结论都同时具备中文状态说明、责任人、证据路径和未验证范围。

#### P0-2：统一运行 manifest 和 episode

- 在 `traceability-model` 中增加 `run_id`、`parent_run_id`、`task_id`、`as_of_commit`、`version`、`model_id`、`tool_policy_hash`、`input_artifact_hash`、`output_artifact_hash`、`failure_class`、`latency_ms`、`cost`、`human_intervention`、`replayable` 字段。
- 规定每个中大型 Agent 任务至少生成一个 Markdown 摘要和一个 JSON run manifest；报告不得覆盖旧文件。
- 把“最终答案通过”与“过程可复现、权限合法、证据完整”分开判定。

#### P0-3：工具权限和生产边界策略即代码

- 为 `allowed_paths`、`forbidden_paths`、生产开关、外部网络、真实客户数据和高风险工具建立统一策略快照与哈希。
- 对越权改文件、外部网络、真实客户数据、删除/迁移/部署和支付/退款操作建立拒绝测试；策略不满足时阻断收口。

#### P0-4：统一 CI/Harness 入口

- 建立根目录可发现、可复用的 Harness CI 入口，至少执行编码、项目红线、开发总表、错误账本、证据索引、定向测试和中文治理检查。
- 本地 pre-commit 与 CI 复用同一脚本；被移出提交门禁的治理检查必须在 CI 或周期任务中有明确责任人和产物。

### P1：持续评测、观测和回放增强

- 增加 Harness 专项评测集，至少覆盖：状态冲突、过期快照、越权改文件、缺证据宣称完成、重复全量测试、中文状态回退、错误账本分叉。
- 评测输出必须带数据集版本、评估器版本、阈值、失败分类和与上一基线的差异。
- 在 P0 最小 episode 包基础上扩展恢复点、跨运行比较和趋势留存；换 Agent 时优先消费 episode，而不是重新阅读整段聊天。
- 统一运行事件和 OTel-compatible 字段，持续记录成本、延迟、工具调用、失败分类、人工介入和重试率。
- 扩展中文注释、日志、脚本输出、Issue/PR 模板和术语表的覆盖率；这些工作不阻塞 P0 运行契约，但必须有量化基线。

### P2：自动文档园艺与低风险中文维护

- 周期性扫描断链、重复入口、过期 `as_of_commit`、孤立 task、失效命令、未登记报告和大文件职责评审缺口。
- 清理历史文档、低风险英文文案、非关键脚本输出和多目录镜像；不得覆盖或删除可作为审计证据的历史文件。

## 六、完成标准

本次评审本身完成的标准：

- 本文件成为外部对标与成熟度结论的唯一入口。
- 评审发现已同步到 Harness Skill、追溯模型、协作规则、验证矩阵和项目状态总表。
- P0/P1/P2 后续工作以 `task_id` 登记，不在多个动态文档中另起进度表。
- 定向门禁通过；纯文档/Harness 变更不重复运行全量测试。

后续 P0/P1/P2 任务完成并有趋势证据后，才可把 Harness 评级从 3.0/5 提升到下一阶段。最低前置条件为：

1. 中文治理控制面、统一运行 manifest/episode、策略即代码和根级 CI 入口全部通过。
2. Harness 自评数据集、趋势基线和运行观测持续产出。
3. 文档园艺和低风险中文维护形成周期任务。

### 2026-09-05 复核口径

本轮完成 P1/P2 质量循环加固：CI 汇总会将 artifact 失败写入 job summary 和 annotation，并以汇总步骤失败结束；Harness 自评扩展为 12 项且本地通过 12/12；运行观测已接入 CI manifest，当前本地样本为 12 个运行。上述证据仍属于初始趋势样本，不满足“持续周期趋势”门槛，因此成熟度评级继续保持 **3.0/5**。后续至少需要多个周期的非零 CI/local manifest、可比较 baseline 与失败分类趋势，再评估升级。

P2 维护项：历史归档断链继续按 warning 保留并标注“历史不可复原引用”；低风险中文文案、日志、脚本输出和术语表建立量化基线；GitHub Actions 的 checkout/setup-python/upload-artifact Node 24 兼容主版本已升级，后续仅需跟踪平台弃用通知。

### 2026-09-05 增补（trace: 20260905-harness-evidence-error-loop）

本轮修复 P1/P2 workflow YAML 可解析性并补齐 CI 证据包：artifact index（`build_harness_artifact_index.py`）对报告目录全部文件计算 SHA-256 并校验必需证据集合（含 `.run.json`、候选目录与 summary），失败时仍上传 `backend/reports/harness/**` 且汇总步骤显式失败；同时建立错误候选闭环（`harness_failure_candidate.py` + `review_failure_candidate.py`），候选默认 `pending`、稳定 fingerprint 去重、只有人工 accept 写入根目录 `ERRORS.md`。Harness 自评数据集升级到 1.2.0（18 项）。新增能力仍处于首个实施周期，无多周期趋势样本，成熟度评级继续保持 **3.0/5**；中文治理区分四类口径——静态中文治理覆盖率、CI/运行输出中文可读性、证据包完整性、人工批准与错误入账，其中前两类已量化（coverage=1.0、Summary 固定中文区段），后两类由 artifact index 与 review 记录承担。
