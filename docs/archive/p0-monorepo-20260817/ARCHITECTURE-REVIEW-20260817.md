## 三、逐项详细评估

### 3.1 Monorepo 结构：✅ 通过（附2条建议）

**优点**：

1. `backend/` 与 `miniapp/` 的职责划分与现有 ADR 0002（Platform/Storefront 边界）完全一致，迁移不产生概念冲突。
2. 统一 `docs/` 解决了当前双仓文档漂移的实际痛点——小程序仓的 `docs/api-contract.md` 与后端接口文档长期靠人工同步，合并后契约可以和实现放在同一个 commit 里。
3. 根目录保留单一 `LOGBOOK.md` 和 `AGENTS.md`，符合"AI Agent 首先阅读一份规范"的现有工作模式。

**建议 A1（中优先级）：迁移脚本需排除运行时产物**

当前脚本用 `Copy-Item -Recurse -Force` 全量复制，会把以下垃圾一并带入新仓：

- 后端：`.mypy_cache/` `.pytest_cache/` `.ruff_cache/` `htmlcov/` `coverage.xml` `.coverage` `ngrok.exe`（二进制工具不应入库）`data/bot.db`（本地数据库！含真实客户数据）
- 小程序：`node_modules/` `.codex-tmp/` `reports/`

**其中 `data/bot.db` 含生产客户主档（24,726条客户数据），绝对不能进入新仓库。**

修正方法：在执行复制前，先在两个源仓库目录放置临时 `.gitignore` 并删除上述产物；或在脚本 Step 3/4 中追加显式排除列表。**此项必须在执行 monorepo-merge.ps1 前修复。**

**建议 A2（低优先级）：`docs/api-contracts/` 目录命名**

小程序仓现有 `docs/api-contract.md`（单数），计划书写的是 `docs/api-contracts/`（复数目录）。建议统一为单数文件 `docs/api-contract.md` 放在新仓根 docs 下，避免迁移时产生两份契约。

### 3.3 MVP 路线：⚠️ 有条件通过（发现1个高危问题）

#### 双轨制战略本身：正确 ✅

- "主线 MVP 快速交付 + 支线技术探索存档"符合单人业余项目的资源现实。
- 8周MVP + 8周试运行 + 12周小程序 + 12周上线的节奏对业余时间投入是合理的。
- 与店家确认过"接受功能少但能用的版本"，商业验证路径成立。

#### 🔴 风险 R1（高）：MVP 分支策略错误 —— 不应从 D1 分支删代码，应从 master 拉干净分支

**问题**：MVP-DEVELOPMENT-GUIDE.md 的 Week 1 任务 1.1 写的是"清理D1相关代码：备份分支→删除或注释掉 payment_attempt/account_hold/accounting_outbox→确保系统能启动"。

**但 Git 现状是**：

```
master = b30b2066（B3.5 冻结基线）—— 天然不含任何 D1-A 代码
codex/r4c-ci-evidence = 7afd44b+（审阅分支）—— 包含全部 D1-A/B/C 工作
```

也就是说：**D1 账务核心代码只存在于审阅分支，从未合入 master**。G0 决定记录明确写着"D1-A 不合入 master，等待项目负责人复核放行"。

如果在审阅分支上做 MVP：
1. 要"删除"的是 5 轮整改（B3.x → D1-A.2.1）刚写完的代码，删除过程本身会引入回归风险；
2. MVP 的 commit 会混在 D1 提交历史之上，未来想恢复 D1 工作时 git archaeology 成本极高；
3. 违反 G0 冻结决定中"不改写已归档提交"的原则。

**修正方案（已纳入本报告第六节行动项）**：

```powershell
# 从 master（B3.5 冻结基线）拉出 MVP 分支 —— 天然没有 D1 代码，零删除成本
git checkout master
git checkout -b mvp-2027-june
```

- D1 探索成果保留在 `codex/r4c-ci-evidence` 分支原样存档（打 tag `archive/d1-accounting-20260817` 即可，甚至不需要）。
- Week 1 任务从"删除D1代码"改为"验证 master 基线的对话/知识库/企微能力可用"——这些能力在 v0.132.9 时早已完备（README 功能清单显示 AI 对话、企微集成、订单查询全部 ✅）。
- **这直接把 Week 1-2 的工作量砍掉一半以上。**

#### 🟡 风险 R1-b（中）：生产环境严重脱节未纳入计划

LOGBOOK 与进度清单显示：生产服务器运行 **v0.109.16**（2026-08-10 快照），而本地基线是 **v0.132.14**。中间隔着 schema v018-v027 共 10 个迁移（含 member_balance、points_ledger、coupon_inventory、payment_attempt 等）。

影响：Week 7-8 部署试运行时，如果直接把 MVP 版本推到生产，`apply_migrations.py` 会一次性补 10 个版本的表结构。虽然迁移器"只补未应用版本"，但从未在生产验证过跨 10 个版本的连续迁移。

**修正**：在 P1 阶段（Week 7 前）增加一个任务：先在测试环境演练 v109→v132 的迁移路径，确认 dry-run 报告无缺失表冲突后再碰生产。或者更简单——MVP 首次部署到一台全新的数据库实例（反正 MVP 只需要 FAQ/订单/企微三张核心表），彻底回避存量迁移问题。**推荐后者。**

### 3.4 技术债策略：✅ 通过（附1条补充）

**优点**：

- "店家会不会停用系统"作为判断标准，非常务实，可直接指导日常决策。
- 四条不允许的技术债（数据丢失/订单错乱/错误回复/安全漏洞）覆盖了业务底线。

**补充 B1（中优先级）：隐私数据保护必须列入"不允许的技术债"**

项目已导入 24,726 条真实客户主档 + 10,011 条 openid 关联。这是《个人信息保护法》意义上的个人信息。当前红线里有"禁止硬编码密钥"，但没有数据层面的条款。

建议在技术债策略中追加第五条不允许项：

> ❌ 客户隐私数据明文暴露（日志打印手机号/openid、数据库文件入库、API 无鉴权返回他人订单）

对应的开发期检查点：
1. 日志脱敏（logger 输出手机号必须打码）——现有代码已有此惯例，MVP 重构时不得退化；
2. `data/*.db` 进 .gitignore（与建议 A1 联动）；
3. 订单查询接口必须校验"查询者与订单归属"关系——这一点现有代码已实现（work包1"客户Agent订单归属隔离"已完成），MVP 精简时**不能顺手砍掉这个校验**。

### 3.5 治理简化：⚠️ 有条件通过（发现1个中危问题）

#### 方向正确 ✅

- 保留 LOGBOOK / mistake-ledger / ADR：正确，这三个是防重复犯错的核心资产。
- 停止自动化证据归档（evidence-index + git blob 绑定）：正确，这套机制是为多人审计设计的，单人项目维护成本 > 收益。
- 交接快照降为手动模板：正确。

#### 🟡 风险 R2（中）：pre-commit 从 17 个砍到 3 个过于激进

计划书 6.3 节建议只保留 ruff format / mypy / 核心测试。但审查现有钩子后发现，其中有一类**安全类钩子不能砍**：

| 必须保留（安全/正确性） | 理由 |
|------|------|
| secrets baseline 检查 | 仓库曾做过密钥治理（secrets-baseline-changes.md），砍掉后 AI 生成代码可能重新引入硬编码密钥 |
| SQL 参数化检查（禁 f-string 拼接） | 注入防护，AI 生成 SQL 时的高频错误 |
| SELECT * 检查 | 与参数化同属一类，成本极低 |
| 架构分层检查（api禁导repository等） | AST 检查成本低，防止 AI 生成跨层调用 |

| 可以砍掉（治理类） | 理由 |
|------|------|
| evidence-index 检查器 | 对应停止证据归档 |
| sync-version 自动递增 | MVP 阶段手动管理版本号即可，此钩子在 Windows 上还出过双递增事故（mistake-ledger M-20260812-001/002） |
| check-mistake-ledger hook | 保留脚本但移出提交门禁，改为每周手动跑 |
| 文件体量守卫 | ADR 0004 本身就说"不为压行数机械拆分"，MVP 阶段触发噪音大于收益 |

**修正后的目标**：17 个钩子 → **约 7 个**（4 安全类 + ruff format + mypy 可选 + 核心测试快速集）。既守住安全底线，又消除提交摩擦。
