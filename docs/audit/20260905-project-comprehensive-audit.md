## 执行摘要

### 最终裁决

**正式公开生产上线：No-Go。**

当前代码库可以继续用于开发、调试和受控测试，但不应承担真实用户订单、真实微信支付、退款闭环、人工客服承接或不可逆的本地账务权威切换。阻断原因不是单个页面缺陷，而是资金与资产一致性、消息可靠性、生产身份配置和部署恢复能力尚未形成可证明的闭环。

项目方向判断为正确：代码库已经形成“自研烘焙电商＋AI 客服平台”骨架，覆盖商品、订单、会员、储值、积分、优惠券、知识库、客户画像、企微客服、小程序和管理后台。问题在于，若以“有赞替代并承接真实业务”为验收标准，当前实现仍处在可运行的试验系统阶段，而不是可对外承诺的生产系统。

### 最高优先级结论

1. 账务服务的幂等检查、余额变更和流水写入没有在服务边界上强制统一事务；并发或中途异常可能造成余额与流水事实不一致。
2. 有赞 Webhook 审计仓储内部自提交，可能打破业务写入与审计状态的原子性，破坏外层事务或 savepoint。
3. 微信客服同步会先提交游标，再在另一个阶段入队；游标提交后进程崩溃可能导致消息永久漏处理。
4. 微信客服外部发送成功后才标记持久队列完成，重启或超时会造成重复回复；当前文本发送调用没有传入可用于幂等的 `msgid`。
5. 订单金额同时使用 SQLite `REAL`、Python `float` 和整数分，不能把金额精度和四舍五入行为作为统一合同。
6. 当前本地环境启用 `ALLOW_MOCK_PAYMENT=True`，微信支付关闭；企微员工鉴权默认关闭，且转人工接手人配置缺失。该状态不能被解释为已具备真实支付或真实人工承接能力。
7. 微信支付通知签名校验没有时间戳新鲜度检查；本轮静态检索只确认了退款 Normalizer 和账务补偿组件，未确认实际退款通知入口、持久事件消费和完整退款对账链路已经接通。
8. 限流和后台登录失败计数为进程内内存状态，多 worker、多实例或重启后都不能提供统一的防护效果。
9. 知识库、客户画像和会话摘要直接拼接进入 system prompt，缺少明确的“不可信数据区”隔离，存在 Prompt Injection 和事实污染风险。
10. 部署脚本只输出人工回滚命令，没有自动回滚或发布前后版本切换机制；生产恢复依赖临时人工操作。

## 详细发现

### A-01：有赞 Webhook 审计与业务写入不是同一事务

证据：

- `backend/app/repository/youzan_webhook_event_repo.py:50` 的 `create_received()` 内部直接 `commit()`
- `backend/app/repository/youzan_webhook_event_repo.py:81` 的 `mark_processing()` 内部直接 `commit()`
- `backend/app/repository/youzan_webhook_event_repo.py:114` 的 `mark_result()` 内部直接 `commit()`
- `backend/app/service/youzan/webhook_dispatcher.py:99-108` 在同一 `db_session_scope()` 中执行租约校验、业务处理和 `InboxRepo.mark_processed()`，但业务处理会调用审计记录器

影响：

- 审计状态可能提前提交，而业务写入随后失败，形成“审计显示已处理、业务事实未完成”
- 内层提交可能提交调用方同一连接上的其他未完成写入
- 嵌套事务或 savepoint 场景可能收到错误的 savepoint 状态，调用方无法按预期回滚
- 失败重试依据被污染，可能出现漏处理、重复处理或无法解释的审计记录

整改要求：

1. 审计仓储只提供 SQL 原语，不得在写方法中 `commit()` 或 `rollback()`
2. 由 Webhook 命令统一拥有 UoW，将业务事实、审计结果和 inbox 完成标记一次提交
3. 增加故障注入测试：业务写成功后审计写失败、审计写成功后业务写失败、提交前进程退出
4. 增加 AST 守卫，禁止该类仓储在写方法内部自行提交

### A-02：企微客服游标提交早于消息入队

证据：

- `backend/app/service/wecom/kf_callback_processor.py:136-157` 在 `_sync_and_collect()` 内拉取、收集消息并调用 `mark_success()`
- `backend/app/repository/wecom_kf_sync_repo.py:45-59` 的 `mark_success()` 内部直接提交 `last_cursor`
- `backend/app/service/wecom/kf_callback_processor.py:95-101` 在 `_sync_and_collect()` 返回后才调用 `_enqueue_messages()`
- `backend/app/repository/wecom_kf_sync_repo.py:87-103` 的消息账本写入也自行提交

影响：

当进程在 `mark_success()` 成功提交后、`_enqueue_messages()` 完成前退出时，下一次同步会从新游标开始，旧消息不会再次拉取；消息账本和持久队列也无法证明该消息已被可靠消费。这是客服消息永久漏处理风险，不是单纯的重试延迟。

整改要求：

- 用一个明确的同步命令 UoW 包住“持久化消息、消息幂等账本、游标推进”
- 游标只能在消息进入持久 inbox 后推进
- 队列满时不能丢弃已经从上游确认的消息，应转为持久化失败、退避或人工告警
- 增加“游标提交后进程崩溃”和“队列入库失败”故障测试

### A-03：企微外部发送成功与队列完成标记之间存在重复窗口

证据：

- `backend/app/service/wecom/base_queue.py:80-100` 规定持久消息只有 `_process_one()` 成功返回后才调用 `_mark_persisted_processed()`
- `backend/app/service/wecom/kf_message_queue.py:165-179` 先调用外部发送，再返回成功
- `backend/app/service/wecom/client_kf.py:69-95` 支持传入 `msgid`，但当前文本发送调用 `kf_message_queue.py:167` 没有传入入站 `msg_id`

影响：

若企微已经接受消息但 worker 在完成标记前崩溃，消息会被租约回收并再次处理，导致用户收到重复文本或重复卡片。没有 provider 级幂等键时，系统只能做到至少一次投递，不能做到可控的重复抑制。

整改要求：

- 为每个出站回复生成稳定的业务幂等键，并传入企微支持的消息 ID 或建立本地出站状态机
- 将文本、卡片等多段回复拆为可恢复的出站事实，不要把一整个 AI 回复当成不可分割的副作用
- 明确“已发送但未知结果”的状态，禁止简单按失败重发
- 增加外部成功、响应丢失、进程退出、租约接管的组合测试

### A-04：储值与积分余额变更缺少服务级原子幂等合同

证据：

- `backend/app/service/stored_value/member.py:63-80` 先查流水，再改余额，再插入流水
- `backend/app/service/stored_value/member.py:95-112` 先扣余额，再读取余额，再插入扣款流水
- `backend/app/service/points/ledger.py:36-52` 和 `:65-83` 具有相同的检查、余额变更、流水写入顺序
- `backend/app/migrations/v021_member_loyalty_accounting.sql:40`、`backend/app/migrations/v022_member_stored_value.sql:36` 只提供流水唯一键约束，并不能自动把余额变更和流水插入变成一个业务命令

影响：

- 两个并发请求可能同时通过“流水不存在”检查并各自更新余额
- 后续流水插入失败、连接中断或调用方未包 UoW 时，余额已经变更但流水事实缺失
- `balance_after` 是读取时快照，不足以在并发下证明是哪一次变更产生的余额
- 退款、补偿和对账无法可靠判断实际发生过几次资产变动

整改要求：

1. 以 `member_balance_id` 为账户主键，统一由账户级命令在一个事务中完成幂等占位、余额 CAS、流水和补偿事实
2. 幂等键应在数据库写入时竞争，而不是只依赖先读后写
3. 对余额、流水、退款欠账和订单支付状态建立同一 UoW 清单
4. 用两个独立数据库连接和并发屏障验证“恰一次变更、恰一条流水、失败整体回滚”

### A-05：金额字段和金额转换路径不统一

证据：

- `backend/app/migrations/schema.py:104-118` 将 `orders.total_amount` 定义为 SQLite `REAL`
- `backend/app/service/order/creation.py:92` 将整数分除以 100 后以 Python `float` 保存
- `backend/app/service/youzan/order_parser.py:51-56` 使用 `float(...) * 100` 转整数分
- `backend/app/service/order/payment_notification.py:61-75` 又从 `REAL` 通过 `Decimal(str(...)) * 100` 还原整数分

影响：

- 不同入口可能因二进制浮点、字符串格式和截断顺序产生一分差异
- 订单金额、支付通知金额、折扣分摊和退款金额可能在边界值上不一致
- 账务核对难以证明原始金额和计算金额的唯一来源

整改要求：

- 订单及所有货币事实统一使用整数分或规范化十进制定点字符串
- 有赞金额解析禁止 `float` 中转，明确小数位、舍入方式和非法输入行为
- 将订单总额、支付计划、退款分摊和通知校验全部建立在同一金额函数和同一存储类型上
- 增加 `0.01`、`0.29`、折扣后半分、部分退款累计和极大金额的正反向测试

### S-01：当前运行配置不具备真实支付上线条件

证据：

- `backend/app/config.py:123` 的默认值虽为关闭，但本地运行配置覆盖为开启
- `backend/app/config.py:128-135` 显示 `WECHAT_PAY_ENABLED=False` 及真实支付关键配置项

影响：

整改要求：

- 生产配置在启动时 fail-closed：真实环境拒绝 mock 开关，且拒绝微信配置不完整的支付入口
- 将 mock 支付限制在显式测试环境和授权测试主体
- 在 `/ready`、发布脚本和前台支付响应中明确区分 mock 与真实支付
- 真实支付、退款、对账和清理必须取得负责人批准后在授权测试号上验收

### S-02：支付通知新鲜度和退款消费链路仍不完整

证据：

- `backend/app/service/integrations/wechat_pay.py:45-83` 校验签名、证书序列号和签名内容，但没有比较 `wechatpay-timestamp` 与当前时间的最大允许偏差
- `backend/app/api/channels/storefront/payments.py:14-24` 只有微信支付通知入口
- `backend/app/service/order/payment_runtime.py:162-192` 当前入口只处理支付成功通知
- `backend/app/service/order/wechat_normalizers.py:105-234` 已定义退款通知和退款查询 Normalizer，但本轮 `rg` 未发现对应通知路由和完整消费服务

判断边界：

这里不能把“未在本轮静态检索发现”写成“功能绝对不存在”。可以确认的是：当前仓库证据不足以证明退款通知、退款查询、退款状态 CAS、退款资产补偿和通知幂等已经在真实入口闭环完成。

影响：

- 被截获或延迟的合法签名通知可能在业务允许范围外重复进入处理
- 支付通知成功不等于退款状态已被可靠消费
- 外部退款成功、本地余额/积分/券未补偿的状态需要持久化查询和人工复核，否则会形成资金与资产不一致

整改要求：

- 增加通知时间戳新鲜度、事件唯一键、先持久化后 ACK 和重复通知状态机
- 退款通知、退款查询和支付通知分别使用独立 Normalizer、事件键和 CAS
- 为每个退款操作保留不可变支付快照、原额、本次退款额、各资产腿和补偿状态
- 用真实 v3 报文完成通知、查询、超时、重放、乱序和部分退款验收

### S-03：人工承接和企微员工授权未达到生产门槛

证据：

- `backend/.env:24` 中 `WECOM_STAFF_ID` 为空
- `backend/app/readiness.py:152-153` 将接手人缺失直接列为 `handoff_staff_userid_ready` 失败
- `backend/app/config.py:170` 将 `WECOM_EMPLOYEE_AUTH_REQUIRED` 默认设为 `False`
- `backend/app/config.py:171-174` 的员工、企业和运营白名单没有形成当前可证明的生产授权
- 本轮生产预检 28 项中有 2 项失败，其中包括 `handoff_staff_userid_ready` 和 `wecom_employee_auth_ready`

影响：

- AI 转人工后可能没有明确接手人，客户只能得到转人工状态而没有人工响应
- 员工智能机器人若未开启身份鉴权，不能把“企微内可调用”视为“只有授权员工可调用”
- 售后、退款和订单运营动作的责任主体不可审计

整改要求：

- 配置并验证正式接手人或客服接待人员
- 生产强制开启员工身份鉴权，配置企业 ID、员工白名单和运营白名单
- 用真实企微身份验证越权、跨群、非运营员工和身份缺失场景
- 将 readiness 失败作为上线阻断，而不是仅作为提示

### S-04：限流和后台登录防护仅覆盖单个进程

## 分域审计结论

### 架构与分层

总体结构是可维护的：API、Service、Repository、Models 的主方向清晰，根 API 兼容入口与 canonical 子目录已经区分，SQL 大多使用参数绑定，Harness 也提供了分层和红线守卫。

主要缺口是**事务属主没有成为全仓强制合同**。部分账务仓储已经按 B3.5 方向去除自提交，但 Webhook 审计、企微同步和其他历史仓储仍保留写入即提交模式。分层“看起来正确”不能替代跨仓储命令的一致事务。

结论：**结构可继续演进，生产放行前必须完成事务属主统一和直接写入守卫。**

### 订单、电商与金额

商品同步、订单创建、支付状态、优惠券、积分和储值模块已经覆盖目标业务范围；后台订单已具备分页，小程序订单则没有同等能力。订单核心风险不是缺少页面，而是金额存储类型和支付事实模型仍然存在历史混用。

结论：**功能覆盖较完整，货币事实未达到不可争议的账务级标准。**

### 会员、储值、积分和优惠券

项目已经投入较多设计和测试，包含账户、流水、退款、短缺债务、券状态、对账案件和 payment attempt 等概念；这说明方向判断正确。但部分运行时调用仍以手机号、先读后写和局部服务顺序为中心，不能证明账户身份、资产事实和补偿操作在所有入口保持一致。

结论：**设计治理领先于实际运行时闭环；不得因为合同文档和单元测试完善就放开真实资金。**

### 支付与退款

微信支付 v3 支付 Normalizer、验签、解密和支付金额校验已经存在，支付通知也有订单状态 CAS 和交易号认领。正向能力值得保留。

但真实支付关闭、mock 开启、通知新鲜度缺失，以及退款通知消费链路缺少可见的端到端证据，构成独立的 P0。退款 Normalizer 存在不等于退款可运营，必须证明“外部状态、内部操作、资产补偿、重复通知、查询恢复、人工案件”全部可追踪。

结论：**真实支付/退款 No-Go。**

### AI 客服与企微

AI 客服已经具备知识检索、工具调用、客户画像、摘要和 UMP 卡片等产品能力，企微客服也有持久 inbox、同步游标和人工状态检查。

主要问题是输入可信度边界和消息投递语义。当前链路同时面对“不可信内容进入 prompt”和“外部发送结果未知”两个不同类别的风险，必须分别治理，不能只增加提示词文字或重试次数。

结论：**可用于受控试运行，不能承诺无人值守的生产客服可靠性。**

### 小程序与管理后台

小程序页面覆盖面较好，真实登录态、订单、支付关闭版本和配置化页面已经形成。管理后台有 HttpOnly/Secure/SameSite Cookie、Origin 限制和 legacy Bearer 开关等正向控制。

但后台登录保护和请求限流不支持多实例一致性；小程序订单列表也有明确的 50 条截断。小程序发布配置 `miniapp/project.private.config.json:6` 设有 `urlCheck:false`，只能作为本地开发配置，不能作为发布验证依据。

结论：**开发测试可用，规模化运营和生产边界仍需收口。**

### 运维、部署与恢复

容器已设置非 root 用户、资源限制和健康检查，生产预检和 smoke 脚本也提供了基础入口。正向控制存在。

但端口暴露依赖外部环境，部署恢复依赖人工命令，临时密钥清理没有统一失败路径，未达到可重复、可演练的发布标准。

结论：**可以继续用于单机受控部署演练，不能作为无人值守生产发布系统。**

### Harness 与项目治理

这是当前仓库最成熟的部分之一：

- 中文治理检查 `16/16`，六维 coverage `1.0`
- 生产预检能明确暴露接手人和企微员工授权失败
- 数据库结构、知识库有效记录、embedding 缓存和静态业务合约均有检查
- 证据索引、运行 manifest、错误候选和 P0 统一门禁已形成闭环

但 Harness 只能证明“检查被执行且控制面按合同工作”，不能自动证明真实支付、真实企微、外部回调和多实例故障已经通过。当前审计中最重要的管理风险，是把治理门禁通过误读成业务上线通过。

结论：**Harness 控制面可以保留为上线前置条件，但不能替代业务领域验收。**

## 整改路线

### P0：先消除不可接受的事实错误

责任主体：项目负责人＋后端负责人。

1. 统一所有高风险命令的 UoW 属主，移除 Webhook 审计、企微同步和账务关键仓储内部自提交。
2. 固化支付尝试、资产快照、账户主键、账务流水、退款操作和 inbox 事件的不可变事实。
3. 重构企微同步为“先入持久 inbox、再推进游标”，队列满和入库失败必须可观测、可重试。
4. 统一货币为整数分或定点十进制，清除 `REAL/float` 作为货币事实的路径。
5. 完成支付通知时间戳、事件幂等、退款通知/查询、退款补偿和人工案件的端到端闭环。
6. 生产 fail-closed：禁止 mock 支付，补齐真实支付、接手人和员工授权配置。

P0 验收标准：

- 两连接并发测试证明账户变更恰一次、流水恰一条、失败整体回滚
- 业务写入、审计写入和 inbox 完成标记同一 UoW
- 企微游标提交前消息已经持久化且可重放
- 支付/退款通知重复、乱序、延迟和进程退出均有可回放证据
- `/ready` 无 P0 失败，且生产配置不能启用 mock

### P1：完成生产安全和可恢复运行面

责任主体：后端负责人＋运维负责人。

1. 将限流和登录失败计数移到受控边缘或共享存储。
2. 从 URL 查询参数移除有赞 token，轮换可能暴露的凭证。
3. 上传文件做魔数校验、解码、重新编码、像素限制和失败清理。
4. 生产端口只暴露反向代理需要的入口。
5. 部署改为版本化原子切换，失败自动回滚，临时密钥用统一 `trap` 清理。
6. 对知识库、画像和摘要增加来源、版本、可信度、可见范围和 Prompt Injection 防护。
7. 完成真实企微身份、人工接管、客服重复回复和外部 API 超时演练。

P1 验收标准：

- 两个 worker、两个实例和重启场景的安全测试通过
- 部署健康检查失败后自动恢复上一版本，RTO 有测量结果

### P2：改善运营完整性和规模化体验

责任主体：产品负责人＋小程序负责人。

- 结果正确：**否**。核心代码可运行，但尚不能证明真实业务在故障和并发条件下保持资金、消息和资产事实一致。
