## 容量结论

| 方案 | 最低配置 | 适用边界 |
|---|---:|---|
| 最低可运行 | `1 核 2 GB、40 GB SSD、3 Mbps` | 单机、低并发、外置大模型 API、图片走 CDN；仅适合开发测试或极低流量验证 |
| 正式推荐 | `2 核 4 GB` 应用服务器 + `1 核 2 GB` 独立数据库 | 承接订单、支付、会员和 AI 客服的正式低流量环境 |
| 一体化部署 | `2 核 4 GB、40-80 GB SSD、5 Mbps` | 应用、数据库和可选 Redis 放在一台服务器 |
| 缓存 | `256-512 MB Redis` | 登录态、限流、热点商品等需要时增加；不是当前低流量的硬前置 |
| 图片与附件 | 对象存储 + CDN | 避免应用服务器带宽随商品图片访问量线性增长 |

按截图峰值，平均请求量仍处于 `0.1-0.3 请求/秒` 量级，瞬时应用并发通常低于 `10-20`。因此 CPU 不是主要瓶颈，容量设计应优先保证数据库持久化、备份、AI API 超时控制、图片 CDN 和故障恢复。

## 升级触发条件

出现任一条件时，应重新测容量并考虑升级或拆分：

- 应用 CPU 持续 10 分钟超过 `60%`，或内存长期超过 `70%`。
- 应用入口持续超过 `5-10 请求/秒`，或峰值同时在线超过 `50`。
- 数据库连接池、SQLite 写锁等待、磁盘 I/O 或备份窗口成为明显阻塞。
- 商品图片、活动页或直播导流开始由应用服务器直接承载高带宽流量。
- 日活从 `100` 增长到 `500-1000`，或出现秒杀、整点抢购、群发活动等突发峰值。
- 服务器本地运行大模型或向量模型；该场景必须单独配置 GPU，不适用本基线。

## 后续复核要求

- 部署新服务器或扩容前，以真实监控数据重新核对 DAU、峰值 QPS、并发、内存、磁盘和出网带宽。
- 不把店铺后台的访客数或浏览量当成后端容量证明，必须补充应用与数据库指标。
- 发生大促、群发、功能上线或外部平台导流前，重新评估峰值放大倍数。
- 本基线只记录资源规划，不改变真实支付、生产验收和正式上线边界。
