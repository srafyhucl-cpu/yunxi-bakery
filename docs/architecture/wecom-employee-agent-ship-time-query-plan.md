## 二、修复范围（本轮只做两块）

### Bug A：`发货时间/发货日期` 语义修复

目标问法：`发货时间是今天的` / `今天要发货的单` / `明天发货的`。

规则：
- 在 `resolve_order_date_field` 的 delivery_time 命中词中，补 `发货时间`、`发货日期`、`发货时候`、`要发货`、`今天发`、`明天发` 等「发货时点」语义。
- 注意与现有 `发货`（状态词，映射待发货）区分：`发货` 单独出现仍只作状态词；只有出现「发货 + 时间/日期/时候」或「要发货/今天发/明天发」这类**时点**语义时，才把 date_field 切到 `delivery_time`。
- 命中后默认补待处理状态集（复用现有 `needs_preorder_delivery` 同款逻辑），避免只查 TRADE_SUCCESS 导致的结构性 0。

目标效果（`发货时间是今天的`）：
- `date_field=delivery_time`
- 约送日期=今天
- `statuses=待处理状态集`
- `keyword=""`

### Bug B：`时间/日期` 关键词污染修复

- 在 `ORDER_GENERIC_STOP_WORDS` 补 `时间`、`日期`、`时候`、`是`（`是` 已在表内，确认不重复）。
- 目标：任何「…时间/…日期」类问法都不再把 `时间`、`日期` 残留成商品关键词。
- 验收：`发货时间是今天的`、`约送日期是明天的` 的 `keyword` 均为空。

**明确不做**：不动 `发货` 的状态映射；不新增普通数字/手机号查单；不碰按客户查（那属另一份收口计划）。

## 三、列表格式收口（回复太乱的问题）

当前单行（`employee_order_line`，`intelligent_bot_order_format.py:205`）把 7 个字段用 `｜` 挤在一行：

```
尾号 200019｜待发货｜杏好有你 x 1｜192.00 元｜2026-07-05 13:57:09｜约送 2026-07-06 16:00:00｜暂无物流
```

问题：字段多、无层次、下单时间和约送时间并排容易混。

### 方案（待你选一个，默认方案 1）

**方案 1（低改动，推荐）：精简单行字段 + 保留尾号优先**
- 列表场景（LIST/SUMMARY 的「最近相关订单」）单行只保留：尾号、状态、商品、金额、关键时间。
- 「关键时间」按口径二选一：约送口径显示约送时间，下单口径显示下单时间，不再两个都塞。
- 物流状态仅在「暂无物流/异常」时显示，正常有物流不刷屏。

**方案 2（中改动）：两行卡片式**
- 第一行：`尾号 X｜状态｜金额`
- 第二行：`商品｜时间｜物流`
- 更清晰但占屏翻倍，企微里长列表会很长。

**方案 3（按场景裁剪字段）**
- 不同 kind 显示不同字段：履约风险单突出约送时间+物流；成交统计突出金额+状态。
- 最灵活，改动最大，需逐场景定义字段集。

### 建议

方案 1 改动最小、风险最低，且直接解决「下单/约送时间并排混淆」。方案 2/3 视觉更好但改动大、回归面广。

## 五、验收标准

1. `发货时间是今天的` → `delivery_time + 今天 + 待处理状态 + 空 keyword`，能查到今天要发的单。
2. `发货` 单独出现（如 `今天待发货多少单`）仍按待发货状态、下单口径，不误切 delivery_time。
3. `约送日期是明天的`、`发货时间是今天的` 的 keyword 均为空，无 `时间/日期` 残留。
4. 列表单行按选定方案精简，下单时间与约送时间不再并排混淆。
5. 全量测试通过，覆盖率不低于现状门槛。
