更细的改造拆解：每一块补强到底解决什么

下面把本轮改造拆成六个可解释模块。每个模块都对应一个上线前常见风险、一个本地已落地的补强点，以及明天同步生产时可以观察到的验收信号。

客户体验兜底

修改前

LLM API 异常、响应解析失败或工具轮次耗尽时，容易退化成“系统忙”类话术，人工侧不一定及时接住。

修改后

AI 失败原因结构化记录，并触发自动转人工；接手提示优先由 LLM 总结“客户诉求 / 当前卡点 / 建议接手”。

ai_failure_auto_transfer handoff summary 客户不掉线

图片理解与多模态

修改前

图片进入模型时缺少明确观察任务，复杂蛋糕参考图、文字、数量、颜色和异常点可能提取不足。

修改后

图片消息追加观察指令，要求提取款式、文字、数量、颜色、尺寸线索、异常与待确认项。

multimodal prompt 定制蛋糕 减少追问遗漏

运行就绪门禁

修改前

上线前需要人工分别确认配置、数据库、向量、后台产物和通道开关，漏一个就可能生产降级。

修改后

`/ready`、preflight 和 smoke 统一检查关键配置、15 张关键表、知识行、向量缓存、后台 dist、企微/有赞状态。

/ready 22 checks 非敏感布尔门禁

数据库结构修复

修改前

生产库缺表时需要人工判断迁移范围，坏数据库文件也可能被误当成普通缺表处理。

修改后

`apply_migrations.py` 默认 dry-run，只列缺失表；写库必须显式 `--apply`，坏 SQLite 文件会被拒绝继续修。

dry-run first --allow-create 防误建库 missing tables

知识与向量闭环

修改前

知识库为空或向量缓存缺失时，AI 检索增强不可用，但修复顺序和风险边界不够清晰。

修改后

先导入最低可服务知识，再重建 `embeddings.npy/json`；两个脚本都先 dry-run，确认目标库/路径后才 apply。

baseline seed embedding rebuild RAG 可用性

留档审计与复盘

修改前

上线过程主要依赖终端文本和人工复制，难被脚本消费，也难保证上线前后报告不互相覆盖。

修改后

preflight、migration、baseline seed、smoke 都支持 JSON 输出、UTF-8 BOM、`{timestamp}` 展开和拒绝覆盖。

metadata reports/*-{timestamp}.json 可审计

明天同步生产的执行泳道：谁先、谁后、看什么结果

这不是单纯“跑脚本列表”，而是一条有前置条件、写入边界和验收信号的生产同步泳道。默认先 dry-run，只有确认目标库、目标路径和生产域名无误后才进入显式 apply。

操作阶段
1. 预检确认配置、数据库、知识、向量、后台和通道是否 ready。
2. 迁移补齐关键表，尤其是画像、质检、知识缺口和企微同步账本。
3. 知识优先同步真实有赞商品；必要时导入最低可服务知识兜底。
4. 向量知识有效行存在后再重建向量缓存，避免空库生成假 ready。
5. 冒烟对同一目标库、向量路径和服务根地址做最终验证。
只读命令
preflight JSON`--json --output reports/preflight-before-{timestamp}.json`
migration dry-run`python scripts/apply_migrations.py --db-path <目标库>`
seed dry-run`python scripts/seed_baseline_knowledge.py --db-path <目标库>`
embedding dry-run`python scripts/rebuild_embeddings.py --db-path <目标库>`
smoke JSON`--json --base-url <服务根地址> --output reports/smoke-after-{timestamp}.json`
写入边界
不写状态preflight 本身只读，只输出 recovery_plan。
显式 --apply默认拒绝创建新库；需要新库时才加 `--allow-create`。
显式 --apply只插入缺失的 7 条基础知识，已有 seed ref 会跳过。
显式 --apply只有 active_docs>0 时才应该生成或刷新向量缓存。
不写状态冒烟只验证，不修复；失败回到 recovery_hints。
验收信号
failed=0`/ready` 相关门禁全部 ready。
schema ready关键表不再缺失，坏库不会被误修。
active_rows>0知识库至少具备最低可服务内容。
cache ready`embeddings.npy` 与 `embeddings.json` 同时存在且可读。
status=ready最终 smoke 与 `/ready` 均无失败项。

当前本地仍故意不处理的运行时缺口

  • 数据库仍缺 `conversation_reviews`、`customer_profiles`、`knowledge_gaps`、`wecom_kf_message_ledger`、`wecom_kf_sync_states`。
  • `knowledge.active_rows=0`，本地没有写入基础知识，也没有同步真实商品知识。
  • `data/embeddings.npy` 与 `data/embeddings.json` 缺失，向量检索缓存尚未生成。
  • 缺少 `WECOM_STAFF_ID` 或 `WECOM_KF_SERVICER_USERID`，企微人工接手人未配置。
  • 本地 `127.0.0.1:7001` 服务未启动，所以 smoke 的 HTTP 接口检查会因同一根因失败。

这次已经补齐的生产级能力

  • 把“上线前靠人想”变成 `preflight` 自动检查和 `recovery_plan` 顺序修复。
  • 把“可能误写”变成 dry-run 默认只读、`--apply` 显式写入、`apply_mutates_state` 标记风险。
  • 把“终端结果难复盘”变成带 metadata 的 JSON 留档，支持时间戳和拒绝覆盖。
  • 把“AI 失败客户卡住”变成结构化失败原因、自动转人工和客服接手摘要。
  • 把“后台是否新版本难确认”变成 dist 内容标记和观察台值守摘要检查。
