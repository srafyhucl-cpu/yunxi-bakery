# 项目完整开发总表与中文优先管理规范设计

- **updated_at**: 2026-08-29
- **trace_id**: `20260829-project-development-register-and-chinese-governance`
- **parent_trace_id**: `20260829-cleanup-temp-and-agent-governance`
- **status**: draft
- **owner**: 项目负责人（决策）＋ AI 员工（维护与验证）
- **适用范围**: 根仓库、`backend/`、`miniapp/` 及所有并行 Agent 任务

## 一、背景与目标

当前仓库已经有 `AGENTS.md`、`PROJECT-STATE.md`、`LOGBOOK.md`、Harness 文档和任务指令，但状态、任务、分支与证据仍需要依靠 Agent 自觉同步。多 Agent 共用工作区时，容易出现以下问题：

- 使用过期计划书或旧任务快照作为当前方向。
- 同一任务被多个 Agent 重复执行，或修改范围越过授权路径。
- 已完成、进行中、阻塞和历史任务的语义混用。
- 分支事实只存在于聊天或命令输出，没有进入长期项目文件。
- 中文管理信息和机器可解析字段混在一起，导致人工阅读或脚本校验不稳定。

本设计的目标是把 `PROJECT-STATE.md` 建成**唯一的完整开发总表**，并用自动守卫检查其结构和一致性。

## 二、设计原则

1. **单一动态状态源**：当前项目状态、主线任务和分支登记只维护在 `PROJECT-STATE.md`；其他文档只能引用，不得重新定义当前状态。
2. **中文优先**：面向人阅读的标题、描述、决策、风险、验证结论、任务名称和交接说明统一使用中文。
3. **机器标识稳定**：`trace_id`、`task_id`、`status`、`owner`、`as_of_commit`、`version`、路径和 Git 分支名保持 ASCII，避免脚本解析漂移。
4. **技术完成不等于治理关闭**：测试或代码完成后，仍需记录负责人确认、证据状态和下一步。
5. **状态必须有证据**：任何“通过”“完成”“阻塞”结论都要关联命令、退出码、报告路径或负责人决策。
6. **测试按风险分层**：开发期间运行定向测试；功能或模块上线候选收口时执行一次全量测试并记录耗时，较长时进入优化评估。
7. **历史材料不作为执行入口**：历史计划进入 `docs/archive/` 或保留历史横幅，当前 Agent 只能从 `PROJECT-STATE.md` 和当前任务队列开始。

## 三、唯一完整开发总表

`PROJECT-STATE.md` 保留现有资产地图、项目边界和风险信息，并按下面顺序组织：

### 3.1 当前快照

文件顶部必须有以下字段：

```text
updated_at:
as_of_commit:
version:
current_branch:
workspace_state:
state_owner:
```

字段含义：

- `updated_at`：本次状态收口日期，使用 `YYYY-MM-DD`。
- `as_of_commit`：状态快照所依据的真实 Git 提交，必须能被 Git 解析。
- `version`：必须与 `backend/VERSION` 一致。
- `current_branch`：当前工作区实际分支；本轮事实为 `main`。
- `workspace_state`：`clean` 或 `dirty`，并在中文说明中写明原因。
- `state_owner`：唯一允许修改当前状态和日志的 owner。

### 3.2 主线任务总表

主线任务表是任务状态的唯一明细源，至少包含以下列：

| 字段 | 规则 |
|---|---|
| `task_id` | 唯一、ASCII、稳定；例如 `T-P2-001` |
| 任务 | 中文名称和目标 |
| 状态 | 中文显示，并附机器状态码，例如 `进行中（active）` |
| 优先级 | `P0`、`P1`、`P2`、`P3` |
| `owner` | 负责人或协作方 |
| `branch` | 真实分支名；主线任务使用 `main` |
| `as_of_commit` | 任务快照基线 |
| 依赖 | 其他 `task_id` 或 `—` |
| 证据 | LOGBOOK、报告或验证命令 |
| 下一步 | 可执行的中文动作，不写空泛口号 |

机器状态码统一为：

| 中文显示 | 机器状态码 | 含义 |
|---|---|---|
| 已完成 | `completed` | 技术和验收条件均已满足 |
| 进行中 | `active` | 已授权且正在执行 |
| 已阻塞 | `blocked` | 有明确外部条件或决策阻塞 |
| 待处理 | `pending` | 已排队但尚未开始 |
| 已暂缓 | `deferred` | 明确推迟，不进入当前执行队列 |
| 历史 | `historical` | 仅作证据，不得继续执行 |

### 3.3 状态视图

为了让人快速阅读，完整开发总表保留以下视图，但不重复维护完整任务内容：

- **已完成**：列出状态为 `completed` 的 `task_id` 和完成证据。
- **进行中**：列出状态为 `active` 的 `task_id`、owner 和本周下一步。
- **未完成**：列出 `pending`、`blocked`、`deferred` 的 `task_id`、阻塞原因和启动条件。
- **历史**：列出 `historical` 的任务或计划，并链接归档位置。

主线任务总表是唯一状态源，视图只允许引用任务 ID；自动守卫检查同一 ID 在视图中的状态码不能与主表冲突。

### 3.4 分支与快照登记

分支表至少包含：

| 分支或轨道 | 类型 | 状态 | 用途 | 基线 | 负责人 | 允许任务 |
|---|---|---|---|---|---|---|
| `main` | 本仓分支 | 当前主线 | Monorepo 集成与可发布基线 | 当前 HEAD | 项目负责人 | 主线任务 |
| 真实存在的功能/修复分支 | 本仓分支 | 活跃/已合并/废弃 | 单一任务隔离 | 创建提交 | 任务 owner | 绑定 `task_id` |
| `D:\Project\YunxiBakeBot` | 外部历史轨道 | 冻结 | D1 审阅与历史证据 | 旧仓提交 | 项目负责人 | 仅明确批准的审阅任务 |
| `D:\Project\YunxiBakeMiniApp` | 外部过期副本 | 停用 | 迁移前参考 | 旧仓快照 | 项目负责人 | 不得作为开发入口 |

外部路径必须标记为“非当前 Git 分支”，不得写入 `current_branch`。不存在的分支不得提前登记为事实；计划中的分支只能放在“候选分支”说明中。

## 四、中文优先规范

### 4.1 文档语言

- 根 README、项目状态、任务指令、交接、LOGBOOK、ADR、验证报告的叙述和结论使用中文。
- 文件名优先使用中文或稳定的英文技术名；不得为了翻译技术路径而制造别名。
- 错误提示、守卫输出和交接摘要使用中文；命令、路径、提交 SHA、包名和 API 字段保持原样。
- 历史英文文档不强制全文翻译，必须增加中文历史说明和当前入口指向。

### 4.2 任务字段

任务元数据键保持稳定：`owner`、`status`、`status_label`、`as_of_commit`、`version`、`allowed_paths`、`forbidden_paths`。`status` 使用固定 ASCII 枚举，`status_label` 使用中文状态并附机器码；页面和表格优先展示中文状态。

### 4.3 分支命名

Git 分支名继续使用 ASCII，推荐 `codex/<topic>` 或仓库现有命名。分支目的、绑定任务、创建基线和合并状态必须在 `PROJECT-STATE.md` 用中文登记。

## 五、自动守卫

新增只读脚本：`backend/scripts/check_project_development_register.py`。脚本不修改文件、不创建报告，只返回检查结果。

检查项目：

1. `PROJECT-STATE.md` 必填元数据存在且格式正确。
2. `version` 与 `backend/VERSION` 完全一致。
3. `as_of_commit` 是真实存在的 Git 提交。
4. `current_branch` 与当前工作区分支一致，且只登记一个当前分支。
5. 主线任务 `task_id` 唯一，状态码属于允许枚举，必填列完整。
6. 已完成、进行中、未完成和历史视图中的任务 ID 存在于主表，且状态不冲突。
7. `docs/tasks/*.md` 均具备 `owner`、`status`、`status_label`、`as_of_commit`、`version`、`allowed_paths`、`forbidden_paths`。
8. 任务指令的 `status_label` 与 `status` 映射一致，`version` 与 `backend/VERSION` 一致，`as_of_commit` 可解析。
9. 分支表登记的本仓分支真实存在；外部轨道明确标为非 Git 分支。

守卫接入一条执行链：

- `backend/scripts/check_project_development_register.py` 可单独运行，适合状态文档收口和故障定位。
- `backend/scripts/check_project.py --skip-tests` 调用该守卫；现有 `.pre-commit-config.yaml` 的 `check-project` hook 因此自动覆盖每次提交，避免重复执行两套相同检查。

守卫失败时输出中文原因、文件路径、任务 ID和修复提示；不自动替 Agent 猜测状态。

## 六、协作生命周期

1. Agent 启动：读取 `AGENTS.md`、`PROJECT-STATE.md`、`LOGBOOK.md` 前 30 行、Harness 入口和本轮任务指令。
2. 领取任务：确认唯一 owner、基线提交、版本、允许路径和禁止路径。
3. 并行执行：只修改授权路径；发现状态或版本冲突立即回报 owner。
4. 更新状态：owner 在主线任务表和状态视图中同步状态，其他 Agent 不直接覆盖全局状态。
5. 收口验证：记录命令、退出码、证据路径、测试耗时和未验证项；全量测试不在开发迭代中重复运行。
6. 分支收口：记录创建基线、合并提交、废弃原因或保留期限；未真实创建的分支不得写成已存在。
7. 任务结束：更新 LOGBOOK、必要时生成 handoff，并运行项目总守卫。

## 七、验收标准

本设计完成后的最低验收条件：

- `PROJECT-STATE.md` 含当前快照、主线任务总表、四类状态视图和分支登记表。
- 现有 5 份任务指令均能通过统一元数据检查，并保留历史/活动语义。
- 当前分支登记准确反映只有 `main` 的事实，不虚构功能分支。
- 项目总守卫和独立守卫均返回 EXIT=0。
- 规范和任务说明以中文为主，机器字段保持稳定 ASCII。
- `LOGBOOK.md` 和交接文档记录本轮 trace、验证结果、工作区状态和遗留风险。
- 证据索引存量问题单独登记，不因本设计而伪造“全绿”。

## 八、明确不在本轮范围内

- 不删除或重写业务数据、有效报告和冻结旧仓。
- 不把不存在的远端分支、生产状态或真人验收写入当前事实。
- 不在没有负责人批准的情况下执行真实支付、退款、客户数据导入或正式上线。
- 不为追求文件行数而拆分业务代码。

## 九、单一进度入口与最小阅读集

### 9.1 “同一个规范”的准确边界

项目的**进度事实**只写入 `PROJECT-STATE.md`：任何新任务、任务状态变化、主线调整、分支变化、阻塞、负责人决策、下一步和完成证据，都必须回写同一个主线任务表或对应状态视图。其他文档不得另起一套“当前进度”。

项目的**静态规则**仍写在 `AGENTS.md` 和 `docs/AGENTS/multi-agent-coordination.md`；接口、发布、数据库和代码实现细节继续放在各自的专业文档或源码附近。这样既保持单一进度入口，又避免把一个文件变成无法维护的百科全书。

### 9.2 新改动点的回写规则

每个改动点按以下顺序回写：

1. 开始前：在 `PROJECT-STATE.md` 建立或认领任务行，写明 `task_id`、状态、owner、分支和基线。
2. 执行中：状态、阻塞、分支、依赖或下一步发生变化时，先更新任务行，再继续扩大工作范围。
3. 完成时：将状态改为 `completed`、`blocked` 或其他准确状态，附命令、退出码、报告路径或负责人决策。
4. 较大任务收口：同步 `LOGBOOK.md`；需要换 Agent 时补交接文档。

代码改了但没有对应任务行，不能宣称项目进度已更新。自动守卫可以检查任务行、字段和引用是否完整，但不能替代 owner 判断“代码变化是否真的完成了业务目标”。

### 9.3 最小阅读集

为了知道项目当前进度，Agent 不需要通读所有文档或所有代码：

- 所有任务：`AGENTS.md` + `PROJECT-STATE.md`。
- 执行具体任务：再读对应的 `docs/tasks/*.md`。
- 涉及小程序接口、发布、支付或真机：只追加读取对应契约/发布清单。
- 涉及证据、复盘或交接：再读取 Harness 相关文档和 `LOGBOOK.md` 最新条目。
- 修改代码时，只检查任务允许路径及其直接依赖，不要求全仓通读。

`LOGBOOK.md` 是时间顺序证据，不是当前状态入口；`docs/archive/` 和历史计划不得用于判断当前进度。
