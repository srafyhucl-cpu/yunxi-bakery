# MiniApp 自提订单核心闭环测试优先设计

## 1. 背景

当前 MiniApp 已具备商品浏览、购物车、自提结算、订单创建、支付准备、模拟支付、订单列表和订单详情能力。现有自动化证据主要覆盖页面展示和“购物车进入结算”，尚未证明以下完整成功链路：

```text
商品 -> 购物车 -> 自提结算 -> 创建订单 -> mock 支付 -> 订单详情
                              \-> 创建未支付订单 -> 取消 -> 订单状态回写
```

本轮不先假设存在业务缺陷，也不先重构结算页。先用测试确认后端和小程序页面的真实行为；只有测试复现出确定的业务问题，才进入对应代码修复。

## 2. 范围

### 包含

- 本地后端的自提订单 API 集成测试。
- 本地微信开发者工具中的 MiniApp 自提订单生命周期测试。
- 覆盖商品有效性、创建订单、`prepare-payment` 回退 `mock`、`mock-pay`、订单详情读取、待支付记录清理和取消订单。
- 测试报告、失败分类和环境阻塞记录。

### 不包含

- 北京闪送真实报价、建单和回调。
- 真实微信支付、真实商户参数和真机验收。
- 生产环境数据、生产域名、生产 API 或生产凭证。
- 与订单闭环无关的 UI 重构、支付抽象重写或后端架构调整。

## 3. 测试设计

### 3.1 后端 API 集成测试

在现有小程序订单 API 测试中新增一条完整成功链路测试，使用测试数据库和合成商品：

1. 写入一个库存充足的测试商品。
2. 通过 `POST /api/v1/miniapp/orders` 创建自提订单，提交真实门店自提地址、合成联系人和合法预约时间。
3. 断言返回 `pending` 订单、服务端计算的商品金额和自提地址快照。
4. 调用 `POST /api/v1/miniapp/orders/{orderId}/prepare-payment`，断言无微信商户配置时返回 `mode=mock`、`paymentMethod=mock` 和 `action=mock-pay`。
5. 调用 `POST /api/v1/miniapp/orders/{orderId}/mock-pay`，断言订单变为 `paymentStatus=paid`、`paymentMethod=mock`。
6. 调用 `GET /api/v1/miniapp/orders/{orderId}`，断言详情中的支付状态、支付方式、履约方式、自提地址和订单时间线与创建结果一致。

取消路径继续复用现有“用户取消待确认订单并释放库存”的 API 测试；新增测试不重复扩大后端取消契约。

### 3.2 MiniApp DevTools 生命周期测试

新增独立脚本，强制使用本地后端和 DevTools 运行态，不读取生产订单、不使用真实微信支付。测试流程：

1. 预检 `http://127.0.0.1:7001/health` 和 DevTools Automator 连接。
2. 通过 `wx.login` 和本地 `/api/v1/miniapp/auth/login` 获取测试会话。
3. 从本地商品接口选择至少一个在售、库存不少于 2 件且可购买的商品。
4. 写入购物车并进入购物车页，再通过页面动作进入结算页。
5. 使用自提联系人、手机号、预约时间和已同意协议状态调用页面自身 `submitOrder()`；用确定性的 `wx.showModal` 测试替身确认支付。
6. 等待页面跳转到订单详情，断言 `paymentStatus=paid`、`paymentMethod=mock`、履约方式为自提、门店地址和商品明细存在。
7. 断言购物车已清空、`yunxiPendingOrder` 已删除。
8. 重新写入同一商品并进入结算页，调用 `submitOrder()` 时让确认弹窗返回取消，得到一笔待支付订单；再调用页面 `cancelPendingOrder()`。
9. 通过订单详情或服务读取断言订单状态为 `cancelled`，并断言待支付记录已清理。

脚本结束时恢复原有购物车、会话和本地 API 存储设置。报告写入 MiniApp 既有 `reports/button-runtime` 证据目录，不覆盖上一份报告。

## 4. 失败处理与安全边界

- 本地后端未启动、DevTools 未连接、测试商品不存在或库存不足时，报告 `blocked`，退出码为 2，不写成业务失败。
- API 返回非 2xx、订单状态错误、支付状态未更新、存储未清理或页面未跳转时，报告 `fail`，保留断言详情。
- 不使用生产 API、生产账号、真实客户信息或真实支付凭证。
- 合成订单只进入本地测试环境；报告只记录必要的订单标识和断言结果。
- 测试报告属于审计证据，不作为临时文件删除；一次性进程、缓存和失败候选仍按项目白名单清理规则处理。

## 5. 通过标准

### 后端阶段

- 新增集成测试通过。
- 现有订单 API 定向测试通过。

### MiniApp 阶段

- `npm run typecheck` 通过。
- `npm run check:miniapp` 通过。
- DevTools 生命周期报告为 `pass`，且没有 `fail` 检查项。

### 缺陷处理

- 若任一测试失败，先保留失败报告和最小复现步骤，再按真实触发路径定位。
- 只有确认是当前业务代码导致 P0/P1 行为错误时，才修改业务代码，并补充针对该缺陷的回归断言。
- 测试全通过时，本轮只收口验证证据，不把“缺少历史自动化覆盖”包装成代码缺陷。
