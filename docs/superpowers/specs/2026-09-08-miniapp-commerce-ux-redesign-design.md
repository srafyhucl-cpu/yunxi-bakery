# 芸熙烘焙小程序商品优先型 UI/UX 与履约重构设计

> 状态：已确认设计
> 日期：2026-09-08
> 适用范围：`miniapp/` 前台小程序、Platform 前台订单与配送契约
> 首发边界：北京闪送 + 门店自取；全国配送不纳入首发

## 1. 背景与目标

芸熙烘焙是北京单店，经营约 12 年。当前有数百个商品，但真正高频成交集中在少量畅销商品；商品、价格、库存和分类在开发阶段主要由有赞数据同步到自研 Platform，小程序只消费自研接口。日常销售额为几千元级，节假日约 1 到 2 万元级。

当前小程序的重构目标不是建设连锁商城或大型电商，而是建设一个商品优先、预订清晰、履约透明、金额准确的单店交易工具：

1. 用户快速找到畅销商品。
2. 用户理解商品是否可买、通常何时履约。
3. 用户能在支付前看到准确的北京闪送费。
4. 用户能够选择北京闪送或门店自取并完成下单。
5. 门店能够处理次日预订、当天咨询、制作和配送异常。
6. 长尾商品可通过分类和搜索找到，但不挤占首页主路径。

## 2. 已确认的业务事实

- 商品预订为主，通常前一天预订、次日发货或取货。
- 当天订单可以接受，但需要根据制作进度与门店能力确认。
- 每日最早发货时间为 09:00，最晚发货时间为 19:30。
- 常规当天订单截止时间约为 17:00；该时间用于提示和引导，不作为不考虑现货情况的绝对承诺。
- 北京范围配送使用闪送，配送费根据收货地址和距离计算，由客户承担。
- 商品价格按自提价格制定，不将快递费摊入商品价格。
- 门店自取与北京闪送并列存在；全国配送是节日场景能力，不进入首发。
- 闪送开放平台尚未申请，首发前必须完成申请、接口验证和受控测试。
- 闪送配送费要求支付前确定，并与商品金额一并支付。
- 有赞继续作为迁移期商品和经营数据来源，但不作为自研小程序新订单的配送报价、支付或闪送运单中间层。
- 当前小程序和 Platform 尚未具备自研闪送报价、配送费入单、配送单创建和回调闭环。

## 3. 产品结构

### 3.1 首页

首页采用“精选商品 + 分类 + 条件化复购”的分层结构：

1. 店铺身份：芸熙烘焙、北京单店、12 年经营作为轻量信任表达。
2. 搜索入口：直接进入真实商品目录。
3. 精选畅销商品：使用现有精选商品配置，展示少量核心商品。
4. 履约说明：提前一天预订、发货时段、当天订单需确认、配送费单独计算。
5. 分类入口：只展示真实分类接口返回且有商品的分类。
6. 最近购买：仅对已登录且存在历史订单的用户展示；无记录时不占固定版面。

首页不平铺数百个商品，不建设门店选择器，不加入无数据来源的评价、销量或活动承诺。

### 3.2 商品列表

商品列表默认精选/畅销优先，提供全部商品和真实分类入口。商品卡统一展示：

- 真实商品图；
- 商品名；
- 自提价；
- 可预订/库存有限/售罄等可验证状态；
- 提前预订或当天咨询提示；
- 进入详情或加入购物车动作。

前端不得根据库存数字臆造制作时长或配送承诺。没有完整制作配置时使用保守说明：通常提前一天预订，当天订单联系客服确认。

### 3.3 商品详情

详情页必须支持朋友圈直达，不依赖首页上下文即可完成判断：商品图、名称、价格、规格、真实状态、预订提示、已有商品说明、北京闪送/门店自取、当天订单提示、加入购物车、立即购买和联系客服。

### 3.4 结算

结算先选择履约方式：

- 门店自取；
- 北京闪送。

门店自取不增加配送费。北京闪送必须填写或选择收货地址，并在支付前调用自研 Platform 的闪送报价能力。报价成功后展示商品金额、配送费、优惠和最终应付金额；报价失败、过期、超范围或平台不可用时不得按 0 元支付，转为重新报价或联系客服确认。

### 3.5 订单

订单详情分别展示：

- 订单制作状态：待支付、已确认、制作中、待取货/待配送、已完成、已取消；
- 闪送状态：未创建、待接单、已接单、取货中、配送中、已送达、配送异常；
- 商品金额、配送费、优惠、抵扣和最终支付金额快照；
- 预约时间、履约方式和联系客服入口。

自提订单不展示闪送状态。

## 4. 技术架构

```text
微信小程序
  -> Platform 前台 API
     -> 商品目录、订单、支付、会员资产
     -> 配送报价编排
        -> DeliveryProvider
           -> ShansongProvider
              -> 闪送开放平台
```

### 4.1 小程序边界

小程序只负责收集输入、请求报价、展示状态和金额、提交订单、展示履约进度及客服兜底。小程序不计算配送费，不保存闪送密钥，不生成签名，不判断最终金额，不直接访问闪送平台。

前端服务边界建议包括：

- `miniapp/miniprogram/services/delivery.ts`：配送报价和配送状态适配；
- `miniapp/miniprogram/services/orders.ts`：订单契约和金额响应；
- `miniapp/miniprogram/utils/order-summary.ts`：金额展示适配；
- `miniapp/miniprogram/utils/checkout-time.ts`：预约时间展示和校验。

### 4.2 Platform 边界

建议在现有分层内新增配送领域，不把平台调用写入页面或订单路由：

- `backend/app/api/channels/storefront/delivery.py`：前台报价路由；
- `backend/app/service/delivery/`：报价、过期、重试、创建和状态编排；
- `backend/app/repository/delivery_quote_repo.py`：报价持久化；
- `backend/app/repository/delivery_order_repo.py`：配送单和回调持久化；
- `backend/app/models/delivery.py`：稳定领域模型；
- `ShansongProvider`：闪送字段映射、鉴权、签名、错误转换和回调验签。

内部适配器接口应支持 `quote`、`create_order` 和 `cancel_order`，使未来替换配送平台不影响订单和小程序契约。

## 5. 数据契约

### 5.1 履约方式

新契约使用：

- `pickup`：门店自取；
- `beijing_delivery`：北京闪送。

首发不开放 `nationwide_delivery`，但领域模型保留扩展空间。兼容期后端可将旧值 `delivery` 映射为 `beijing_delivery`，小程序新代码不再发送含义过宽的 `delivery`。

### 5.2 报价接口

```http
POST /api/v1/miniapp/delivery/quotes
```

请求包含 `fulfillmentMethod`、收货人、手机号、收货地址、预约时间和商品 ID/数量。服务端重新读取实时商品价格、库存、上下架和配送参数，不信任前端价格。

成功响应核心字段：

```json
{
  "quoteId": "dq_xxx",
  "status": "quoted",
  "provider": "shansong",
  "goodsTotalFen": 19800,
  "deliveryFeeFen": 2600,
  "quoteTotalFen": 22400,
  "currency": "CNY",
  "expiresAt": "2026-09-08T16:30:00+08:00",
  "estimatedDurationMinutes": 75
}
```

状态包括：`quoting`、`quoted`、`expired`、`address_out_of_range`、`provider_unavailable`、`pending_confirmation`。`deliveryFeeFen: null` 表示未确定，不能支付；`0` 仅用于自提或平台明确报价为零的情况。

### 5.3 创建订单

配送订单必须携带 `deliveryQuoteId`。服务端创建时验证报价归属、有效期、地址、商品和数量、商品价格、库存和预约时间。任一项发生变化都要求重新报价。

### 5.4 金额快照

订单和订单详情返回并持久化：

```json
{
  "goodsTotalFen": 19800,
  "deliveryFeeFen": 2600,
  "discountFen": 1000,
  "couponDeductionFen": 500,
  "pointsDeductionFen": 200,
  "balanceDeductionFen": 0,
  "payableFen": 20700,
  "currency": "CNY"
}
```

计算规则为：商品金额 + 配送费 - 各项优惠和抵扣。旧客户端可暂时读取 `totalFen`，新客户端以明细和 `payableFen` 为准。历史订单不能按当前商品价格重新计算。

### 5.5 配送状态

配送快照保存 `provider`、`quoteId`、`providerOrderId`、`status`、`deliveryFeeFen`、取货地址、收货地址、预计时长和最后同步时间。内部状态包括：`not_applicable`、`pending_create`、`created`、`accepted`、`picking_up`、`delivering`、`delivered`、`cancelled`、`failed`。

闪送回调必须按外部事件 ID 幂等落账，避免重复创建配送单、状态倒退或重复执行取消。

## 6. 分阶段实施

### Phase 0：基线与范围冻结

盘点当前 15 页面、接口、测试和工作区改动，建立页面状态矩阵，冻结首发为北京闪送 + 门店自取，全国配送独立于首发。

### Phase 1：闪送申请与能力验证

申请开发者和商户能力，取得正式文档，确认鉴权、签名、测试环境、回调、门店地址、重量/体积/件数要求、报价有效期、错误码、取消和退款规则。测试近距离、远距离、超范围和不可服务地址，形成 Go/No-Go 结论。

### Phase 2：Platform 配送领域与金额契约

实现配送领域模型、报价和配送单持久化、`DeliveryProvider`、`ShansongProvider`、报价接口、订单金额快照、报价绑定校验、过期校验、回调幂等和功能开关。优先保证自提订单不受影响，配送报价失败不能支付。

### Phase 3：小程序交易链路

重构首页、商品列表、详情、购物车、结算、订单、地址和个人中心。接入履约方式、闪送报价、金额拆分、报价过期、客服兜底、预订说明和配送状态。

### Phase 4：视觉与交互系统

完成“温暖精品烘焙 + 现代极简电商”统一设计：暖白、可可棕、少量奶油金；减少绿色、渐变、玻璃拟态和装饰性阴影；统一商品卡、状态标签、价格组、履约选择、金额明细、订单时间线、空态和错误重试。

### Phase 5：DevTools 与测试环境验收

覆盖 15 页面渲染、精选和长尾商品、直达详情、自提、闪送报价、报价过期、超范围、平台不可用、金额组合、待支付恢复、订单取消、订单配送状态、未登录、售罄、图片失败、慢网和控制台错误。代码测试、DevTools 走查、闪送接口测试、金额状态机测试和真实支付/退款验收分开记录。

### Phase 6：切换准备

稳定商品同步和门店精选维护，配置生产闪送回调和监控，完成自提/北京闪送回归、切换演练、金额核对、异常处理和回滚方案。全国配送继续作为后续专项，不阻塞首发。

## 7. 验收原则

- 不以静态文案替代闪送报价接口验收。
- 不以模拟支付冒充真实支付验收。
- 不允许报价失败按零元配送费支付。
- 不把有赞历史 `post_fee_fen` 当作新小程序订单配送费真相。
- 不在小程序本地计算配送费或最终金额。
- 不因页面视觉通过而宣称订单履约闭环完成。
- 结果正确、策略合法、证据完整、可回放四项分别记录。

## 8. 非目标

本轮不建设多门店体系，不把全国配送纳入首发，不重做有赞商品同步主链路，不新增没有事实来源的评价/销量/会员权益，不在小程序内实现 AI 对话、订单持久化、支付回调或配送平台密钥逻辑。
